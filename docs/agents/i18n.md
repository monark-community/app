# i18n guidelines

Practical rules for internationalization in this monorepo, for agents and humans. Read this before adding or touching any user-facing string, i18n key, or module registry description. Two goals: correct and complete translations for real user chrome, and NOT translating the technical surface (which is where drift and runtime "missing key" bugs come from).

## TL;DR

- Translate **user-facing chrome and content**. Do NOT translate **technical identifiers or operator / builder descriptions** ; those are canonical English strings that live in code and module registries.
- Every `t("key")` you add must be added to **both** `en.json` and `fr.json`. `check:i18n` only verifies that en and fr carry the _same_ key set ; it cannot catch a key that is missing from _both_ locales (it renders as a raw key path at runtime).
- Keep ICU placeholders (`{count}`, `{category}`) identical across locales.
- Data-driven / dynamic labels are not i18n ; if one must render through `t(\`ns.${x}\`)`, add a `t.has(...)` fallback so a miss degrades to a readable string instead of a key path.

## What to translate, and what not to

### Translate (goes in `services/web/src/messages/{en,fr}.json`)

Anything a **general end user reads in their own language**:

- UI chrome: labels, buttons, menu items, empty states, tooltips, `aria-*`, table column headers, validation messages shown to users.
- User-facing content: notification **templates** (the subject / body a user actually receives ; these live per-locale in the owning module's `templates/`, en + fr), account / profile pages, emails.

### Do NOT translate (canonical English, lives in code / module registries)

Technical tokens and the operator / developer / builder-facing text that describes them. The audience is technical, the strings map to code and external APIs, and translating them creates a large drifting surface for no user benefit. (This mirrors how n8n works: it localizes the editor shell, not the node / event / integration layer.)

| Thing                                                            | Where it lives                                | In the i18n catalog?         |
| ---------------------------------------------------------------- | --------------------------------------------- | ---------------------------- |
| Domain event type id (`user.signed-in`) + its description        | `registerEventTypes("<mod>", { … })`          | No ; English registry string |
| Permission key + description                                     | `registerPermissions("<mod>", { … })`         | No ; English registry string |
| Feature-flag key + description                                   | `registerFlags("<mod>", { … })`               | No ; English registry string |
| Automation node type / label / description + config-field labels | node `descriptor` (`registerAutomationNodes`) | No ; English registry string |
| Notification kind id                                             | code                                          | n/a ; it is an identifier    |

The load-bearing pattern: a registry `description` is product-authored English content served to the operator / builder UI directly. The RBAC role editor renders each permission **description** raw from the registry (`p.description`), and the automation editor renders node labels and trigger event options raw from the descriptor / event-type registry (`desc.label`, the dotted `e.type` id). None of those go through the i18n catalog.

### The split that trips people up

A module surface usually has **both** a translated part and an English part. Get the boundary right:

- **RBAC role editor**: the **category header label** is i18n (`admin.rbac.editor.categories.<category>`) ; the **permission descriptions** under it are English registry strings.
- **Automation editor**: the **editor chrome** (buttons, search, preflight messages, `automation.editor.*`) is i18n ; the **node labels and trigger event options** are English registry strings.
- **Notifications**: the **email / in-app template** a user receives is per-locale (en + fr) in `templates/` ; the kind's **label + description in the prefs UI** is i18n (`account.notifications.prefs.kinds` / `kindDescriptions`) ; the kind **id** and the event / operator wiring are English.

Rule of thumb, three questions:

1. Does a general end user read this in their language? Then **i18n (en + fr)**.
2. Is it a technical identifier, or an operator / developer / builder description that maps to code or APIs? Then **English registry string, not i18n**.
3. Is it a data value (a record's name, user input, a per-model or per-row label)? Then **not i18n at all** ; it is content. Render it directly, and if it must pass through `t()`, use a fallback (below).

## How i18n works here

- **next-intl v4.** Catalogs: `services/web/src/messages/en.json` (the reference locale) and `fr.json` (mirrors it). Consume with `const t = useTranslations("some.namespace")` then `t("key")` ; `t("a.b")` resolves nested keys (a `.` means nesting).
- **Ids as keys**: a dotted id used as a key is flattened with `id.replaceAll(".", "_")` (e.g. `auth.new-device` becomes `auth_new-device`), because `.` is nesting.
- **`check:i18n`** (`pnpm check:i18n`, a CI gate, `tools/check-i18n.ts`) enforces that every locale carries the **exact same key set** as en. It intentionally does not compare values (many en / fr values are legitimately identical: brand names, ICU skeletons, cognates).

## The gate's blind spots (where the bugs come from)

`check:i18n` is parity-only. It cannot catch:

1. **A key missing from _both_ locales.** Write `t("x.y")` but never add `x.y` to en or fr, and parity still holds ; it renders the raw key path (`x.y`) at runtime. This is the number-one i18n bug in this repo.
2. **Placeholder drift.** If `fr` drops a `{count}` that `en` has, rendering breaks ; parity of _keys_ does not notice.
3. **Dynamic keys.** `t(\`categories.${x}\`)`, `t(kindKey)` cannot be resolved statically by any check.
4. **Dead keys.** Keys present in both locales but referenced nowhere.

So: **adding a `t()` call is not done until the key exists in both `en.json` and `fr.json`.** Do not rely on the gate to remind you.

## Rules when adding or changing keys

- Add every new key to **both** locales, same path. Write a real French translation (not a copy of English), except for brand names, cognates, and ICU skeletons.
- Keep **placeholders identical** across locales.
- Prefer **static string-literal keys** (`t("editor.save")`) over dynamic ones ; they are greppable and would be caught by type-safe keys if that lands.
- For **dynamic display labels** (per-model, per-record, or otherwise data-driven), do not invent i18n keys. If a value is unavoidably rendered through `t(\`ns.${x}\`)`, add a fallback so a missing or dynamic key degrades gracefully:
  ```ts
  label: t.has(`categories.${cat}`) ? t(`categories.${cat}`) : cat,
  ```
  This is what the RBAC role editor does for dynamic `Data Model: <name>` categories.
- **One source of truth per label.** Do not copy a label into a second namespace ; reuse the existing one. (The dev-overlay notifications panel reuses `account.notifications.prefs.kinds` via a `.`→`_` transform instead of maintaining its own kind-label map.)
- When you register a **new module**, decide up front where each of its strings lives using the table above: wire the registry `description`s in English, and add i18n only for the user-facing chrome.

## Verifying

- Run `pnpm check:i18n`, but remember it is parity-only ; also eyeball that the key is present in en (and that you added the fr side).
- The full pre-PR gate must pass: `pnpm gen && pnpm typecheck && pnpm lint && pnpm test && pnpm check:tiers && pnpm check:modules && pnpm check:i18n`.

## Recommended tooling (NOT yet implemented ; propose, do not assume it exists)

These would close the blind spots above:

- **Type-safe message keys**: declare `interface IntlMessages` from `en.json` so `t("missing.key")` becomes a **compile error** caught by `pnpm typecheck`. Covers the static-key majority (dynamic template keys still bypass it).
- **Placeholder-parity check**: extend `tools/check-i18n.ts` to assert each locale's ICU `{args}` match en per key.
- **Runtime missing-key surfacing**: wire next-intl's `onError` to a dev-overlay panel plus an e2e assertion, to catch the _dynamic_ misses that static tooling cannot.

## Adding a new locale

The infrastructure is already N-locale: `check:i18n` compares every `*.json` against en, so a new file is automatically held to completeness.

1. Add `services/web/src/messages/<code>.json` with the full key set (mirror en ; a scaffolder that clones en's structure helps).
2. Register the locale in the next-intl config (locale list, request config, middleware).
3. Translate the values. An agent can draft the bulk (preserving ICU placeholders and house tone), with the placeholder-parity check and a human review as the quality gate.

A bonus of the convention above: technical and registry strings are not in the catalog, so a new locale never has to (re)translate event, permission, flag, or node descriptions.

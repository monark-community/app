# @monark/data-models

Admin-configurable, polymorphic "Data Model" engine (Notion-Databases style). Admins define their own record types (name + fields + types + limits) at runtime, with no app code change or deploy. The legacy bespoke `Project` / `Industry` modules have been dropped and now live as Data Models on this engine (their data was migrated over).

Spec: [docs/features-planning/phase-2/polymorphic-db.md](../../docs/features-planning/phase-2/polymorphic-db.md).

**Status: shipped end-to-end.** `DataModel` + `DataField` + `DataRecord` CRUD, two-layer RBAC (per-model permissions + per-record role access), the `registerModelIntegration` registry (consumed by `@monark/calendar`'s materialization subscriber), opt-in per-field expression indexing, per-model webhook event types, computed `FORMULA` fields (a shared safe expression engine, compute-on-write), and the admin schema-builder + generic record UI (below). Remaining gaps are in "Deferred".

## What's here

- `/contracts` — `DATA_FIELD_TYPES` / `DataFieldType` (mirrors the Prisma enum), `fieldConfigSchemas` (per-type `DataField.config` shape), `valueSchemaFor` / `valueSchemaForField` / `stripHtmlTags` (the shared record-value zod builder — see "Key concepts"), the formula engine (`formula.ts`: `evaluateFormula` / `tryEvaluateFormula` / `coerceFormulaResult` / `extractFieldRefs` / `parseFormula` / `FORMULA_FUNCTIONS` — the shared, safe expression evaluator for `FORMULA` fields, see "Key concepts"), `registerModelIntegration` / `listModelIntegrations` / `getModelIntegrationDef` (the integration-slot registry — see "Key concepts"), and `DataModelsEvents`.
- `/server` — Prisma data layer (`data.ts`: models + fields + records + model-integrations CRUD, key/slug derivation and collision helpers, title derivation), `data-models.{manage-schema,read-schema,record-read,record-write,record-bulk-write,record-delete,view-all-records,manage-forms}` permissions (`permissions.ts`), the `dataModelsRouter` tRPC sub-router (`router.ts`), and event-type registration (`event-types.ts`).
- UI (in `services/web`) — the admin schema builder ([admin/data-models/[id]/model-editor.tsx](<../../services/web/src/app/(authed)/admin/data-models/[id]/model-editor.tsx>) + [field-editor-dialog.tsx](<../../services/web/src/app/(authed)/admin/data-models/[id]/field-editor-dialog.tsx>)) and the generic record list/detail UI ([data/models/[modelKey]](<../../services/web/src/app/(authed)/data/models>)), both built on the `services/web/src/components/fields` toolkit.

Prisma models live under `// ── MODULE: data-models ──` in `packages/db/prisma/schema.prisma`: `DataModel`, `DataField`, `DataRecord`, `DataModelIntegration`, `DataFieldIndex`, `DataRecordRoleAccess`, `DataRecordWatcher`, `DataModelWatcher`, `DataRecordView`. The `DataFieldType` enum gained `FORMULA`, `FILE`, and `ATTACHMENTS` members (a computed field ; a single-file field ; a multi-attachment field). Migrations: `20260706000312_add_data_models` … `20260802140000_add_data_record_views`.

## Key concepts

**Hybrid storage.** Fixed, indexed Postgres columns for the system envelope (`id`, `organizationId`, `key`/`slug`, `title`, timestamps) + a single JSONB `data` column on `DataRecord` for admin-defined field values, namespaced by `DataField.key`. Avoids both a full EAV join-per-field design and a bespoke-columns-per-model design. See the spec's "Data model" and "Edge cases & risks" sections for the tradeoffs this accepts (relation fields have no real FK ; fast filtering on a hot field is opt-in via `DataFieldIndex`, not automatic for every field).

**Every Data Model is org-scoped.** `DataModel.organizationId: string` (non-null) — platform-wide (null-org) models are disallowed. Key uniqueness is per-org and scoped to LIVE rows only, so a soft-deleted model frees its key for reuse. Prisma's `@@unique` can't express that NULL-aware condition, so it's a hand-written partial index rather than a schema `@@unique`:

```sql
CREATE UNIQUE INDEX "DataModel_org_key_active_unique"
  ON "DataModel" ("organizationId", "key") WHERE "deletedAt" IS NULL;
```

Every model create/access check resolves the caller's active org (`requireOrg`) and gates on `requirePermission(ctx, "data-models.manage-schema", org.id)`. There is no platform namespace and no `scope` input — `models.create` always writes `organizationId = org.id`, and `models.getByKey` / `resolveDataModelByKey` resolve a key within the caller's org alone. (Historically `organizationId` was nullable, with `null` meaning platform-wide to mirror `Industry`; the [20260707050000_data_models_org_required](../db/prisma/migrations/20260707050000_data_models_org_required/migration.sql) migration re-parented any null-org models + records to the singleton org and made the column NOT NULL, and [20260707060000_data_models_key_unique_partial](../db/prisma/migrations/20260707060000_data_models_key_unique_partial/migration.sql) restored the soft-delete-frees-the-key partial unique.)

**Each model auto-integrates into RBAC + webhooks as it's created.** On create (and refreshed on rename), a model registers three per-model record permissions — `data-models.<key>-record-{read,write,delete}` — and three per-model event types — `data-models.<key>-record-{created,updated,deleted}` — grouped under `Data Model: <name>` in the `/admin/rbac` catalog and the webhook subscription picker. `requireModelAccess` accepts EITHER the per-model permission OR the generic `data-models.record-*` (admins short-circuit both), so a role can be granted just one model's records without the blanket grant, and existing grants keep working. The engine still emits the generic `data-models.record-*` event ; it carries the per-model type as `DomainEventBase.subscriptionAliases` so the webhooks matcher routes the generic emit to a per-model subscription (per-model event _literals_ can't join the codegen'd `DomainEvent` union, hence the registry + alias split). Both registries are in-memory ; `hydrateDataModelRegistrations()` re-walks every live model at api boot to rebuild them after a restart. See [server/registrations.ts](src/server/registrations.ts).

**Isolated by an org-scoped visibility layer.** The per-model entries are globally registered (so `isKnownPermission` + grant-time validation pass, and the picker has their metadata) but marked `orgScoped`. The two display readers — `/admin/rbac`'s `adminListPermissions` and `webhooks.listEventTypes` — only SHOW an org the org-scoped entries a registered visibility resolver reports for it. `registerDataModelVisibilityResolvers()` (wired at boot) registers resolvers returning exactly the caller-org's LIVE models' keys, so one org never sees another org's model keys — even though the registry entry is shared (two orgs with a `project` model map to the single `data-models.project-record-read`, which is correct: enforcement scopes by the model's org, and a shared key stays grantable wherever the model exists). The generic hooks live in `@monark/rbac` (`registerOrgScopedPermissionVisibility`) and `@monark/common` (`registerOrgScopedEventTypeVisibility`), keeping those packages ignorant of `data-models`.

**One validation implementation, shared client/server.** `valueSchemaFor` (in `/contracts/field-types.ts`) builds the zod fragment that validates one field's _value_, given a structural `DataFieldValueShape` (type + the config properties that affect validation) and optional message overrides. `services/web/src/components/fields/schema.ts`'s `schemaFor` is a thin adapter from the client's `FieldDef` onto this same function — the server (no i18n, messages omitted) and the client (localized `FieldMessages` passed in) share one implementation instead of two hand-synced ones. `valueSchemaForField(type, config, required)` is the server-facing entry point that also validates the field's persisted `config` against `fieldConfigSchemas[type]` first.

**Field keys are immutable JSON property names.** `DataField.key` (`^[a-z][a-z0-9_]*$`) is the literal key inside every `DataRecord.data` blob for that field — renaming it would silently orphan existing values, so the API only ever offers a `label` edit after create. `DataModel.key` is a separate, dash-case machine name (`^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$`) used as a route segment, matching the `Organization` / `Project` slug shape.

**Archiving, not deleting, a field.** `DataField.archivedAt` hides a field from the create/edit form and column picker, but past records' values under that key stay readable — deleting a field definition outright would make historical `DataRecord.data` unparseable against the current schema.

**A record's title is denormalized and recomputed on every write.** Every model owns a reserved required TEXT field with key `title` (auto-created on model creation, protected from archive / delete / retype), and `DataRecord.title` is that field's value — a fixed convention, not an admin-chosen title-field pointer. A blank value falls back to `"Untitled"` for display. `update` re-validates the _full_ merged object (existing `data` overlaid with the patch), not just the patched keys, so a partial edit can't silently leave a required field's constraint violated.

**`FORMULA` fields are computed, read-only, and recomputed on every write.** A `FORMULA` field's config is just `{ expression }` ; its value is derived from _other fields on the same record_ by a small safe expression language (no `eval`) — column references (by field key), arithmetic (`+ - * / %`), string concat (`&`), comparisons, `&&`/`||`/`!`, and a Notion-like function library (`if`, `round`, `concat`, `dateAdd`, …). The result **type isn't configured** — `inferResultType` derives it from the expression's outermost operation (comparisons/logic → BOOLEAN, arithmetic → NUMBER, `&`/text functions → TEXT, date functions → DATE), so there's no redundant, drift-prone type field to keep in sync ; a bare reference or an `if`/`coalesce` with disagreeing branches falls back to TEXT, and an explicit cast (`toNumber(...)`, `toString(...)`, `toBool(...)`, `toDate(...)`) is the override that pins the type. The derived type drives coercion-on-write, the record cell renderer, and the sort accessor. Because compute happens on record write, **adding a formula field (or changing its expression) backfills existing records** via `recomputeModelRecords` — otherwise a formula column would render empty on every record that predates the field (the form preview computes live, but the table shows the stored value). The backfill skips records whose output is unchanged (the title comes from the reserved TEXT `title` field, which no formula can change, so it's never touched here). The engine (`contracts/formula.ts`: tokenizer → recursive-descent parser → tree-walking evaluator) is pure and isomorphic, so the **same** implementation evaluates server-side on write (`applyComputedFields`, the authoritative value persisted into `DataRecord.data`) and client-side for the live preview a formula field renders in the record form — one engine, the same seam `valueSchemaFor` uses for validation. Compute-on-write means formula columns are stored like any other value (filterable / sortable / indexable). v1 is **same-record only** (no cross-record rollups). On the write path formula keys are stripped from client input (never trusted) then recomputed ; formulas that reference other formulas evaluate in dependency order (a topological sort). At field-save time the expression is validated against the model: every reference must resolve to a real sibling field (never itself), and the formula dependency graph must stay acyclic (`A → B → A` is rejected). A formula that fails to evaluate degrades to `null` — the engine is total, it never throws at eval time.

**Record access is two-layered : per-model permission, then per-record role access.** _Model layer_ — a record op gates on the per-model `data-models.<key>-record-<verb>` OR the generic `data-models.record-<verb>` (admins short-circuit) : can you touch this model's records at all. _Row layer_ — within a model you can access, a `DataRecord` with no `DataRecordRoleAccess` rows is visible to everyone (the default, fully backward-compatible) ; with rows, only those roles may read/edit/delete it. A restricted record is a **404** (not 403) for callers whose roles aren't listed, so its existence doesn't leak. Bypassing the row layer is its own capability, **`data-models.view-all-records`** (which ADMIN/SYSADMIN short-circuit) ; note a blanket `data-models.record-read` does **not** bypass it, and neither does `manage-schema` — row-level is real privacy, not overridden by "read all" or by "can edit the schema". Revoking `view-all-records` from a role is how you get a data steward who designs schemas but cannot read restricted rows. Until [20260908120000_split_record_visibility_permission](../db/prisma/migrations/20260908120000_split_record_visibility_permission/migration.sql) the bypass was implied by `manage-schema` ; that migration backfills the new permission onto every role that held `manage-schema`, so the split is a no-op on upgrade. The filter mirrors `CalendarRoleAccess` (`server/data.ts`'s `recordRoleAccessWhere`). Set a record's access with `records.setAccess` ; read it with `records.getAccess`.

**Watchers + notifications.** A user can watch a single record (`DataRecordWatcher`) or a whole model (`DataModelWatcher`) — "watch this page" / "subscribe to the database", Notion-style. On any `data-models.record-{created,updated,deleted}` event, the `record-watch-subscriber` fans out an in-app `data-models.record-changed` notification to the union of (record watchers ∪ model watchers), **minus the actor** (no self-notifications) and **minus anyone the record's row-level access hides it from** (cheap short-circuit when the record is unrestricted). This is the module's Notifications integration (registered kind `data-models.record-changed`, IN_APP + opt-out-able, one kind covers all three change types via an `action` var). Watching is a per-user preference gated on read access (not admin-only, unlike per-record access) : `records.setWatch` / `records.isWatching`, `models.setWatch` / `models.isWatching`, with Follow/Following toggles in the record panel + full-page editor and the model list header.

**Mapping, not reserved field keys, for module integrations.** A module (e.g. `@monark/calendar`) declares named "slots" it needs — a type constraint, whether it's required, and (for `RELATION`) a `relationTarget` — via `registerModelIntegration(module, { slots, description })` at boot, mirroring the `registerPermissions`/`registerFlags` idiom. An admin then maps their own Data Model's fields onto those slots per-model (`DataModelIntegration.slotMappings`, a `slotKey -> DataField.id` map), validated by `upsertModelIntegration` against the registry (unknown module, wrong field type, mismatched `relationTarget`, or a required slot left unmapped while `enabled: true` are all rejected). Nothing here assumes any particular field key name — an admin free to name their own fields however they like, which is the whole point : reserved key names would force a fixed vocabulary onto a no-code surface and can't express "which of two date fields" or a relation-shaped requirement like "which calendar" at all.

**Dates round-trip through JSONB as strings, not `Date` instances.** `DataRecord.data` is JSON, which has no native Date type — a `Date` written on create comes back as an ISO string on the next read (e.g. inside `updateDataRecord`'s re-validation of the merged object). `valueSchemaFor`'s `DATE`/`DATETIME` branch preprocesses either a `Date` or a valid date string into a `Date` before validating, so both the client (real `Date` objects from a date picker) and the server (strings read back from storage) validate correctly and get a `Date` back from `.parse()`.

**Per-field indexing is opt-in, not automatic.** The baseline GIN index on `DataRecord.data` (added in the first migration) makes every field filterable _correctly_ from day one, but a fast query plan on a hot field at scale needs a real expression index. `fields.requestIndex` (`server/indexing.ts`) provisions one on demand : a B-tree over the extracted-and-cast value for scalar types (`((data->>'key')::numeric)` for `NUMBER`, `::boolean` for `BOOLEAN`, `::timestamptz` for `DATE`/`DATETIME`, plain text for everything else), or a GIN over the raw jsonb array for `MULTI_SELECT`/`RELATION`. `CREATE INDEX CONCURRENTLY` can't run inside a transaction and can take a while on a large table, so `requestFieldIndex` returns immediately with `"pending"` and the build runs fire-and-forget in the background ; poll `fields.indexStatus` or `DataField.indexed` to know when it lands. Idempotent : a field already `pending`/`building`/`ready` short-circuits, and `CREATE INDEX CONCURRENTLY IF NOT EXISTS` covers the remaining race. The field's `key` and both its id and its model's id are re-validated against a strict regex immediately before use, since none of this DDL has a parameterized form for identifiers or jsonb paths — interpolating them directly is only safe because they're already validated at field-creation time and never come straight from request input at this layer.

**Structured query language (MonarkQL), separate from formulas.** The generic language — the `FilterNode` AST (predicate leaves + boolean groups), the operator / `FilterableKind` taxonomy, the text DSL (`parseQuery` / `printQuery`), and `@variables` — lives in the shared **`@monark/query`** package (also used by kanban) ; `contracts/query.ts` here is a thin adapter that re-exports it plus the `DataFieldType → FilterableKind` bridge (`filterableKindOf`). Record filtering builds that canonical tree from both the filter menu and a text query bar, compiled to raw SQL by `server/query-compiler.ts` and run by `listDataRecordsWithQuery`. It's deliberately **not** an extension of the `FORMULA` engine : a formula is a per-record compute (one scalar out of one loaded record, in JS), a query is a set selector (a predicate over the whole table, compiled to a `WHERE`). The compiler emits `Prisma.Sql` (not Prisma's structured JSON `where`) so text filtering can be case-insensitive (`ILIKE`) and so comparisons hit the **expression indexes** `indexing.ts` builds — Prisma's `data: { path, gt }` form would miss them. Field keys are interpolated as identifiers (safe : validated + immutable, same guarantee the indexing DDL relies on) ; every value is bound as a parameter. Keyset pagination + the record role-access filter are preserved as SQL, so the compiled path is access-identical to the structured one. The text DSL (in `@monark/query`, `parseQuery` / `printQuery`) serializes the same tree (`status:open -assignee:present`, `priority:>3`, `tags:&a,b`, `due:2026-01-01..2026-06-01`). Values may be `@variables` (`@me`, `@today`, `@startOfWeek`…) resolved at compile time against the caller + "now". A dotted field **traverses a relation** one level (`assignee.title:alice`) — compiled to an `EXISTS` over the target model's records, scoped to the caller's readable rows. **Saved views** (`DataRecordView`, `dataModels.views.*`) persist a named tree per model — personal or shared — editable only by its owner. Gated behind `data-models.query-language` (default off). Full detail : [docs/technical-documentation/data-model-queries.md](../../docs/technical-documentation/data-model-queries.md).

**Public forms let non-users submit records.** An admin publishes a `DataForm` for a model (gated `data-models.manage-forms`, flag `data-models.public-forms`) exposing a chosen **subset of field keys** (`fieldKeys`) ; everything else stays private (e.g. a `status` field the admin maintains). Two modes : `ANONYMOUS` (a shareable `/f/<token>` capability link, per-IP rate-limited) and `EMAIL` (each recipient gets a unique SHA-256-hashed, single-use key, mailed via `sendMail` — the `Invite` pattern). The public `forms.public.{get,submit}` procedures are `publicProcedure`s that authorize from the **token**, never `ctx`/`requireOrg` (anonymous requests have no session), resolving org + model from the `DataForm` row. A submission is validated against ONLY the exposed fields (`recordDataSchema(publicFields)` — which strips any private key a submitter injects), non-exposed fields are defaulted, `title` is auto-generated when not exposed, and the record is written via the normal `createDataRecord` with a sentinel `createdBy = "public-form:<id>"`. The form-save rule requires every required field (except `title`) to be on the form, so a submission never fails on a missing private required value. Only simple field types are exposable (`PUBLIC_FORM_FIELD_TYPES` — no relation / file / document / formula). Tables : `DataForm` + `DataFormInvite` (`base.prisma`) ; data layer `server/forms.ts`.

**A public form can also be a moderated public board (read side).** With `listEnabled`, the form exposes a searchable, read-only list of its entries (feature requests / bug reports / Q&A). Every submission becomes a `DataFormEntry` (`PENDING`) — invisible to the public until an admin **approves** it (`forms.entries.publish`) ; `forms.entries.reject` hides it. The board exposes its OWN read allow-list `listReadFieldKeys` — SEPARATE from the writable `fieldKeys` — so a `status` field is publicly _readable_ but not publicly _writable_. `forms.public.list` / `forms.public.record` return records **projected** to `listReadFieldKeys` (via `projectPublicRecord`) — the raw `DataRecord.data` (private fields, submitter email) never leaves the server ; `listDataRecords` gained a `publishedForFormId` relation-filter so board search/pagination reuse the record engine, scoped to `PUBLISHED` entries. Read access is per-form (`listPublicRead` : anyone-with-the-link vs invite-gated).

**A model can opt into engagement : voting + discussions.** Two per-model toggles (`DataModel.votingEnabled` / `discussionsEnabled`, set via `models.update`) turn on record-level engagement that surfaces on the public board. **Engagement is never anonymous** — the identity is a real principal, so no cookie/visitor substrate is needed. **Voting** (`DataRecordVote`) accepts a logged-in user _or_ a board invite ; the dedup key is `voterKey = "user:<id>" | "invite:<id>"`, enforced by `@@unique([dataRecordId, voterKey])`. `forms.public.vote` toggles a vote ; the board gains a `sort: "top"` that ranks by vote `_count` (opaque offset cursor, since keyset-on-a-count isn't practical). **Discussions** (`DataRecordComment`) are **user-only** (a logged-in `User` authors them — no invite / anonymous path), **auto-published**, with admin moderation : `hidden` (kept, not shown publicly) + `deletedAt` (author or `manage-forms` admin). Bodies are tag-stripped on write (no stored HTML). `forms.public.comments.{list,post,remove,setHidden}` ; a `post` emits `data-models.record-commented`, which notifies the record's watchers. Data layer `server/engagement.ts` (kept form-agnostic so it can later serve the authed record view). Tables in `base.prisma`.

| `forms.entries.pending` / `publish` / `reject`                 | `data-models.manage-forms`                                                    | board moderation queue ; `publish` emits `data-models.form-entry-published`                                                                                                                                                                                                                                                                                 |
| `forms.public.get` / `submit`                                  | _(none — token-authorized)_                                                   | anonymous ; resolve the form from the token (+ invite key for EMAIL mode), flag-gated by `data-models.public-forms`, submit rate-limited per IP                                                                                                                                                                                                             |
| `forms.public.list` / `record`                                 | _(none — token-authorized)_                                                   | the public board : searchable list (`sort: recent \| top`) + detail of PUBLISHED entries, **projected to `listReadFieldKeys`**, with vote/comment counts ; read-access gated (`listPublicRead` / invite key), rate-limited                                                                                                                                  |
| `forms.public.vote` / `voteState`                              | _(token-authorized ; identity required)_                                      | toggle / read the caller's upvote on a published record (requires `votingEnabled` + a logged-in user or invite ; anonymous → 403), rate-limited                                                                                                                                                                                                             |
| `forms.public.comments.list` / `post` / `remove` / `setHidden` | _(token ; `post` login-only ; `remove`/`setHidden` author-or-`manage-forms`)_ | discussions on a published record (requires `discussionsEnabled`) ; auto-published, admin-moderated ; `post` emits `data-models.record-commented`                                                                                                                                                                                                           |
| `forms.public.canModerate`                                     | _(none — token-authorized)_                                                   | non-throwing : whether the logged-in caller may moderate this board's comments (drives the moderation UI)                                                                                                                                                                                                                                                   |

## Usage

```ts
// Server-side, another module reading the field-value contract:
import { valueSchemaForField } from "@monark/data-models/contracts";

const schema = valueSchemaForField(field.type, field.config, field.required);
const value = schema.parse(input.data[field.key]);
```

```ts
// A module declaring its integration slots at boot (e.g. @monark/calendar's
// packages/calendar/src/server/model-integration.ts):
import { registerModelIntegration } from "@monark/data-models/server";

registerModelIntegration("calendar", {
  description: "Materializes a Data Record onto a Calendar as a real CalendarEvent.",
  slots: {
    time: { types: ["DATE", "DATETIME"], required: true, description: "..." },
    calendarRef: {
      types: ["RELATION"],
      relationTarget: "Calendar",
      required: true,
      description: "...",
    },
  },
});
```

registerDataModelsPermissions();

## Dependencies

- `@monark/db` (Prisma)
- `@monark/common` (event bus, errors, tRPC primitives, pagination)
- `@monark/organizations` (`requireOrg`)
- `@monark/rbac` (`requirePermission`)

Core tier — every org needs the engine, and it must be depended on by other modules (`@monark/calendar`'s materialization subscriber, and temporarily `@monark/projects`'s planned compatibility shim), which an extended-tier module can't provide for another extended module.

## Events emitted

| Event                              | When                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-models.schema-changed`       | A `DataModel`, `DataField`, or `DataModelIntegration` is created, edited, reordered, or saved (`kind: "model" \| "field" \| "integration"`) |
| `data-models.record-created`       | A new `DataRecord` was created                                                                                                              |
| `data-models.record-updated`       | A `DataRecord`'s fields, title, or slug changed ; `changed` carries the `DataField.key`s + `title`/`slug`                                   |
| `data-models.record-deleted`       | A `DataRecord` was soft-deleted (`hard: false`) or hard-deleted (`hard: true`)                                                              |
| `data-models.form-submitted`       | A record was submitted through a public form (anonymous link or email invite) ; the submit path ALSO emits `record-created`                 |
| `data-models.form-entry-published` | An admin approved a public-form submission onto the public board (now visible + searchable)                                                 |
| `data-models.record-commented`     | A user posted a comment on a record (discussions) ; notifies the record's watchers                                                          |

All three record events carry `dataModelKey` alongside `dataModelId` so a subscriber (e.g. Calendar's materialization subscriber) can filter by model without a round-trip lookup.

The record-watch subscriber ([record-watch-subscriber.ts](src/server/record-watch-subscriber.ts)) also consumes `data-models.record-commented`, fanning a new comment out to the record's watchers (`data-models.record-commented` notification kind, IN_APP). Notifying an external email-invite submitter (not a `User`) is a deferred follow-up.

## Events consumed

None yet. (`@monark/calendar` is the first consumer of `data-models.record-*` — see its README's "Events consumed".)

The admin schema builder ([admin/data-models/[id]/model-editor.tsx](<../../services/web/src/app/(authed)/admin/data-models/[id]/model-editor.tsx>)) is built : model settings, full field CRUD with drag-reorder, per-type config for all field types — text/number/date/select/relation/formula plus **`FILE`** (single, format-constrained) and **`ATTACHMENTS`** (many, MIME allow-list + max count ; values are soft `StoredFile.id` references validated server-side against `@monark/files`), **`RICH_TEXT`** (Tiptap HTML) and **`DOCUMENT`** (a Notion-style BlockNote block editor ; value is a block-array JSON, title/search/index derived via `blocksToText` in `@monark/common/blocks`, non-filterable) ([field-editor-dialog.tsx](<../../services/web/src/app/(authed)/admin/data-models/[id]/field-editor-dialog.tsx>)), the "indexed" badge + `fields.requestIndex` affordance, and the `DataModelIntegration` slot-mapping section. The generic record list/detail UI ([data/models/[modelKey]](<../../services/web/src/app/(authed)/data/models>)) is built on `services/web/src/components/fields`.

## Deferred

- **Registry hygiene on hard delete.** A hard-deleted model's global registry entries linger until the next boot re-hydrates only live models. It's already hidden from every org's picker the moment the model is gone (the visibility resolver drops it), so this is cosmetic — the entry just isn't garbage-collected until restart.

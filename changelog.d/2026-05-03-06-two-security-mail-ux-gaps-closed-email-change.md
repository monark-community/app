- 2026-05-03: Two security-mail UX gaps closed.

  **Email-change OTP fallback.** Supabase's email-change confirmation puts a 6-digit code in both the old + new address inboxes ; previously there was nowhere to enter it (link was the only path). [email-change-form.tsx](<monark/app/services/web/src/app/(authed)/account/email-change-form.tsx>) now switches to a `<verify>` stage after submit (same pattern as forgot-password) — the form stays mounted with an `<InputOTP>` and prompts for a code from either inbox. New [`verifyEmailChangeOtpAction`](<monark/app/services/web/src/app/(authed)/account/actions.ts>) server action calls `supabase.auth.verifyOtp({ type: "email_change", token, email })` against the new address first (more common, the user opens the unfamiliar inbox first), falls back to the old address. On rotation completion, mirrors the link path's finalisation : sync the shadow row + `signOut` + redirect to `/signin?emailChanged=1`. When only one side has confirmed, the form stays open with a "first side confirmed, now enter the code from {currentEmail}" prompt. **i18n** (en + fr) : new `account.emailChange.{otpInstructions, otpPendingOther, otpPrompt, otpHalfDone, verify, verifying, errors.{missing, invalidCode, notAuthenticated}}`.

  **Password-changed email copy beefed up.** The "If this wasn't you" path was a single button hand-waving toward `/account` ; now the email surfaces a concrete 3-step incident-response checklist (revoke all sessions → reset password again → enable TOTP if not on yet) before the CTA, so the recipient knows what to actually do when they hit the email. Same wiring as before (`changePasswordAction` / `resetPasswordAction` → `auth.notifyPasswordChanged` → `user.password-changed` event → notifications subscriber → `notify("auth.password-changed", …)`) ; verified intact. **i18n** (en + fr) updated in [packages/notifications/src/templates/auth/password-changed.ts](monark/app/packages/notifications/src/templates/auth/password-changed.ts).

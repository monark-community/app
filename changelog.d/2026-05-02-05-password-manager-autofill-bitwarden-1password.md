- 2026-05-02: Password manager autofill (Bitwarden / 1Password / iOS Passwords) detects the auth forms reliably on mobile. Two patterns fixed :

  **1. `autocomplete="username"` instead of `"email"` on sign-in + sign-up** ([signin-form.tsx](<monark/app/services/web/src/app/(anon)/signin/signin-form.tsx>), [signup-form.tsx](<monark/app/services/web/src/app/(anon)/signup/signup-form.tsx>)). The HTML spec reserves `username` for the identity field of an authentication form, even when its value is an email address. Mobile password managers key on this exact token to surface saved credentials ; with `email` they often miss the form entirely (the "password field not detected" UX). Pairs with `current-password` on signin / `new-password` on signup.

  **2. Hidden `username` field in password-change + reset-password forms** ([password-section.tsx](<monark/app/services/web/src/app/(authed)/account/password-section.tsx>), [reset-password-form.tsx](monark/app/services/web/src/app/auth/reset-password/reset-password-form.tsx)). Without an associated identity field, password managers either create a brand-new entry with no username or fail to recognise the form as a password change. The hidden input is read from the authed user's email (or the recovery-flow session's email) ; not displayed, not submitted to the server, just there for the manager to associate the new password with the existing entry.

  No changes needed for `auth.totp` codes (`autocomplete="one-time-code"` is correct), recovery codes (free-form text, manager doesn't need to fill them), or the email-change form (`autocomplete="email"` is correct because it's a new email value, not a sign-in identity).

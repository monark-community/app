- 2026-07-06: Data Models — admin schema-builder + generic record browsing UI, plus two bugs caught in manual verification. Fifth slice of [`@monark/data-models`](monark/app/packages/data-models), landing the frontend on top of the four backend phases : a [`DataField` → `FieldDef` adapter](monark/app/services/web/src/components/fields/data-field-adapter.ts) (`dataFieldToFieldDef`, `recordDataToDefaultValues`) maps a polymorphic field 1:1 onto the existing fields toolkit, so the admin schema editor and the generic record UI reuse `AutoForm` / `fieldColumn` rather than hand-rolling per-type forms. `/admin/data-models` ([data-models-list.tsx](<monark/app/services/web/src/app/(authed)/admin/data-models/data-models-list.tsx>)) is the model list + create panel on the standard `DataTable`/`FilterBar`/`TableDetailLayout` shell ; `/admin/data-models/[id]` ([model-editor.tsx](<monark/app/services/web/src/app/(authed)/admin/data-models/[id]/model-editor.tsx>)) is a full-page editor for settings (name, description, title field), fields (add/edit/reorder/archive/index via a [`FieldEditorDialog`](<monark/app/services/web/src/app/(authed)/admin/data-models/[id]/field-editor-dialog.tsx>) covering all 12 field types' config sub-forms), and a registry-driven Integrations section that renders whatever `dataModels.integrations.listAvailable` returns (Calendar's `time`/`calendarRef` slots today) without hardcoding any module name. `/data/models/[modelKey]` ([records-list.tsx](<monark/app/services/web/src/app/(authed)/data/models/[modelKey]/records-list.tsx>)) is the generic record list + detail panel, gated on `data-models.record-read` / `read-schema` ; every dynamically-registered Data Model gets a sidebar tab alongside the static Projects/Industries entries ([data/layout.tsx](<monark/app/services/web/src/app/(authed)/data/layout.tsx>)).

  Manual end-to-end verification (fresh signup → TOTP enrollment → create a model → add text/number/select fields → set a title field → browse and create/edit a record, driven with Playwright against the real dev stack) caught two real bugs the type checker couldn't : (1) `/data/layout.tsx`, a Server Component, was passing Lucide icon _components_ as a prop into the client `DataSidebar`/`DataTabsBar` for the per-model dynamic tabs — Next.js forbids functions crossing the Server→Client serialization boundary, which hard-crashed the entire `/data` section (including the pre-existing Projects/Industries screens) the moment any Data Model existed. Fixed by carrying a serializable icon key instead (`DataTabIcon = "folderKanban" | "tags" | "database"` in [data-tabs.ts](<monark/app/services/web/src/app/(authed)/data/data-tabs.ts>)) and resolving it back to a component in a client-only `TAB_ICONS` map in [data-sidebar.tsx](<monark/app/services/web/src/app/(authed)/data/data-sidebar.tsx>). (2) The `/admin/data-models/[id]` breadcrumb showed the raw cuid instead of the model's name, because [app-bar-breadcrumb.tsx](monark/app/services/web/src/components/app-bar-breadcrumb.tsx)'s per-pattern dispatch (`pickCrumbForSegment`) never got a case for this new route — added a `DataModelNameCrumb`, matching the existing `UserNameCrumb`/`OrgNameCrumb`/`RoleNameCrumb`/`WebhookNameCrumb` pattern (resolve via `dataModels.models.getById`, fall back to the id while loading/on error).

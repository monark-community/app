  - **Render Blueprint for the api + scheduled jobs** ([render.yaml](monark/app/render.yaml)). One Web Service for the api (`tsx src/server.ts`, port 4000, `/health` healthcheck). Two Cron Job services hit the api with the shared `CRON_SECRET` : `monark-cron-deletions` runs `/cron/process-account-deletions` daily at 03:00 UTC ; `monark-cron-webhook-sweep` runs `/cron/sweep-webhook-deliveries` every 5 min as the external backstop for the in-process worker. Closes the GDPR-class "deletion cron unscheduled" gap. Migrations run via `preDeployCommand` (Prisma `migrate deploy`) so a failing migration aborts the deploy without corrupting the running version. Secrets are marked `sync: false` ; Render prompts the operator on first deploy. New `start:prod` script in [services/api/package.json](monark/app/services/api/package.json) drops the `--env-file=.env` flag so Render's native env injection takes over.
  - **Vercel deploy spec for web** ([services/web/vercel.json](monark/app/services/web/vercel.json) + [services/web/DEPLOY.md](monark/app/services/web/DEPLOY.md)). Build + install commands run from the workspace root (`pnpm gen && pnpm --filter web build`) so workspace packages resolve. `ignoreCommand` skips the build when nothing under `services/web/` or its `@monark/*` dependencies changed (api-only PRs don't burn a Vercel deploy). DEPLOY.md documents the manual UI steps (project root, region pin, `NEXT_PUBLIC_*` env vars).
  - **Production security headers** ([services/web/next.config.ts](monark/app/services/web/next.config.ts) + [services/web/src/middleware.ts](monark/app/services/web/src/middleware.ts)). Added a `headers()` config that returns HSTS (2 years, includeSubDomains, preload-eligible), CSP, X-Frame-Options=DENY, X-Content-Type-Options=nosniff, Referrer-Policy=strict-origin-when-cross-origin, Permissions-Policy (camera/microphone/geolocation/payment all `()`), plus the UA-CH `Accept-CH` / `Critical-CH` opt-in. `connect-src` is built from `NEXT_PUBLIC_API_URL` + `NEXT_PUBLIC_SUPABASE_URL` at build time. Headers return `[]` in dev — HSTS would lock subsequent http://localhost requests and the strict CSP would block Next's HMR overlay. Moved the previously-middleware UA-CH headers into the same `headers()` block so middleware stays focused on auth state ; the comment block in [middleware.ts](monark/app/services/web/src/middleware.ts) cross-links to the new home.
  - **Webhook secret env-var resolver** ([packages/webhooks/src/server/secret-store.ts](monark/app/packages/webhooks/src/server/secret-store.ts)). Single-tenant deploys can now ship without an external secret manager. New `setWebhookSecretResolver(fn)` API + a built-in `makeEnvVarSecretResolver()` that reads `WEBHOOK_SECRETS_JSON` (`{ endpointId: plaintext }` map) with a per-endpoint `WEBHOOK_SECRET_<endpointId>` env-var fallback. Endpoint ids are validated against `^[a-z0-9]+$` defensively before being interpolated into env-var names so a hostile id can't reach into unrelated env vars. `resolveSecret` now consults the registered resolver only after the in-memory cache + activeStore miss, so the dev file-backed flow + just-rotated secrets (cached for the current process) keep working. Wired into [services/api/src/server.ts](monark/app/services/api/src/server.ts)'s `startBackgroundWork` BEFORE `startWebhookDeliveryWorker()` so the first delivery already has a path to plaintext. 14 new unit tests in [packages/webhooks/tests/secret-resolver.test.ts](monark/app/packages/webhooks/tests/secret-resolver.test.ts) cover the JSON map, per-endpoint env vars, malformed-JSON tolerance, endpoint-id validation, and the resolver-throws path.
  - **Trusted-device cookie SameSite=strict in production** ([services/web/src/lib/trusted-device-cookie.ts](monark/app/services/web/src/lib/trusted-device-cookie.ts)). The cookie is the device-recognition signal the (authed) layout reads on every page navigation — flipping to `strict` blocks CSRF-style cross-site rides for it without breaking the dev LAN-cross-origin flow (which keeps `lax`). Gated on `NODE_ENV === "production"`.
  - **`pnpm bootstrap`** ([tools/bootstrap.ts](monark/app/tools/bootstrap.ts)). One command for a fresh checkout : sanity-checks Node 22+ / pnpm / Docker, copies `.env.example` → `.env` for the four services that ship one (never overwrites), runs `pnpm install --frozen-lockfile`, boots Supabase (`pnpm exec supabase start`), and applies Prisma migrations. Idempotent — re-running is a no-op or near-no-op at every step. `--no-supabase` flag skips the docker / migrate steps for the rare case where you bring your own Postgres.
  - **Pre-commit hook** (root [package.json](monark/app/package.json) + simple-git-hooks + lint-staged). `simple-git-hooks` registers the hook on `pnpm install` via the `prepare` script ; `lint-staged` runs ESLint with `--fix --max-warnings=0` on staged `.ts` / `.tsx` files and Prettier across staged JS / JSON / YAML / Markdown. Catches the kinds of issues that have been making CI flaky over the last few rounds before they reach the runner. Typecheck stays in CI ; running `tsc --noEmit` on the whole project on every commit was felt as too slow in the original DX scan.
  - **Prisma postinstall graceful on Windows file lock** ([packages/db/scripts/postinstall.mjs](monark/app/packages/db/scripts/postinstall.mjs)). The `pnpm dev` server holds `query_engine-windows.dll.node` open ; running `pnpm install` while dev is up was failing with `EPERM` on the atomic rename and aborting the entire workspace install. New wrapper runs `prisma generate`, detects EPERM/EBUSY/EACCES on Windows specifically, and downgrades to a warning (the existing generated client is still usable). Real generation errors + non-Windows failures keep aborting the install. Linux CI sees no behaviour change.

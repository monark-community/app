- 2026-08-05: Automation integrations — **shared `@monark/integration-kit` + a manifest `integrates` convention, factored out of the GitHub module.** As more automation integrations land (Slack/Jira/…), the reusable ~80% shouldn't be copy-pasted, and "this extends automation" belongs in metadata, not the folder tree (the glob-derived tsconfig paths + gen tooling assume flat `packages/*`). Two pieces: (1) a new library `@monark/integration-kit` ([src/server](monark/app/packages/integration-kit/src/server)) with `defineInboundWebhook({ secretKey, verify, map, label })` (resolve the org's signing secret → verify → map → `emit` ; 404/401/202), `verifyHmacSha256`, `makeConnectionSecretRouter` (the `status`/`generateWebhookSecret`/`disconnect` connection surface), and `createRestClient` + `pickString`/`pickNumber`. (2) A manifest field `integrates: "@monark/automation"` ([modules.manifest.ts](monark/app/modules.manifest.ts)) with a new `check:tiers` rule that an integration must actually depend on the module it names (metadata can't go stale), plus `getModuleIntegrates` / `listIntegrations` helpers. `@monark/github` is refactored onto the kit — its webhook handler is now a `defineInboundWebhook` call, its connection router a `makeConnectionSecretRouter` call, and its REST client a `createRestClient` — dropping its bespoke HMAC/secret/fetch code while keeping identical behavior (10 github unit + 2 integration still green; 6 new kit unit tests for `verifyHmacSha256`). The integration pattern is documented in [extensibility-contract.md](monark/app/docs/technical-documentation/extensibility-contract.md). Decision: keep the flat package layout (nesting under `packages/integrations/*` would break the tsconfig path globs for modest gain); express the relationship as enforceable metadata + shared code instead. `typecheck` (kit/github/api) + `lint` + `check:tiers`/`check:modules` green.

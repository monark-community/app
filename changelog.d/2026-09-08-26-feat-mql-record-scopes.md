- 2026-09-08: RBAC / Data Models: **a role can now be granted "the records matching this MonarkQL query"** on a model, so access control stops being all-or-nothing per model plus a per-record ACL. New [`DataModelRoleScope`](packages/db/prisma/base.prisma) (`roleId` x `dataModelId` x `verb`, carrying a `FilterNode` tree ; migration [20260908160000_add_data_model_role_scopes](packages/db/prisma/migrations/20260908160000_add_data_model_role_scopes/migration.sql)) expresses "support sees only tickets in their region" or "a rep sees only their own deals" without touching a row. The load-bearing rule is that **roles stay additive**: the effective predicate is the OR, over every role the caller holds that _grants_ the verb on that model, of that role's scope or TRUE when it has none ([`server/scopes.ts`](packages/data-models/src/server/scopes.ts)) ; so one unscoped granting role leaves you unrestricted and a scope only narrows the access its own role confers, which is the only semantic consistent with roles that grant rather than subtract. Enforcement rides the single filter path the earlier convergence created: a scope is AND-ed into the same tree `records.list` already compiles, and the by-id paths run the same compiler against one record via `assertRecordVisible`, so a scope cannot mean one thing in a list and another on a direct link. The side doors are closed too, since global search and the watcher fan-out reach records without going through `records.list` ; both now check, and both keep a fast path (`modelHasAnyScope`) so an unscoped model costs nothing. A scoped-out record is a **404, never a 403**. Everything **fails closed**: a stored scope that fails `filterQuerySchema` denies rather than ceasing to filter, and a scope may not traverse a relation (a traversal reads the target model, so it could depend on rows the scoped role cannot see). Configuring a scope needs the new `data-models.manage-record-scopes`, deliberately **not** `manage-schema` ; whoever can delete a scope can widen their own access, which would undo the `view-all-records` separation ; both changes emit `data-models.record-scope-{set,cleared}` for audit. Only `READ` is enforced in this release (the enum carries WRITE / DELETE so the schema is stable), which is sufficient because you cannot edit or delete what you cannot see ; write-side scoping needs post-write revalidation in a transaction and is its own change. Ships **inert**: no scope rows means today's behavior exactly. 11 integration tests cover the narrowing, the write paths, the additive rule, `@me` resolving per caller, both bypasses, the fail-closed parse, the traversal rejection, the search side door, and that a `manage-schema` holder cannot manage scopes. New doc: [record-scopes.md](docs/technical-documentation/record-scopes.md).

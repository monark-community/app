- 2026-09-09: Auth — **the otplib 13 upgrade locked every existing 2FA enrollment out**; verification now accepts the shorter secrets otplib 12 minted. otplib 12's `authenticator.generateSecret()` defaulted to 10 bytes, so every secret already in the database is 80-bit / 16 Base32 characters. otplib 13 added a `MIN_SECRET_BYTES = 16` guardrail that **throws** `SecretTooShortError` from inside `verifySync` rather than returning `{ valid: false }`, so from the moment the upgrade shipped, `verifyTotpCode` threw on every enrolled account. The throw travelled up through the tRPC boundary into the catch-all in [services/web/src/app/(anon)/signin/totp/actions.ts](<services/web/src/app/(anon)/signin/totp/actions.ts>), which reports anything that isn't a clean `ok: false` as `invalidCode` ; the user saw "that code is invalid" for a correct code from a correctly-synced authenticator, on every attempt, with no way through except a recovery code. [packages/auth/src/server/totp.ts](packages/auth/src/server/totp.ts) now passes `createGuardrails({ MIN_SECRET_BYTES: 10 })` to `verifySync`, which only relaxes what we accept from secrets already stored ; `beginTotpEnrollment` still calls v13's `generateSecret()`, so every new enrollment gets the RFC 4226-recommended 20 bytes. This corrects the `2026-09-08` entry's claim that enrolled users were unaffected because v13 "generates the same 32-character Base32 secret" : that describes v13's own output, not the v12 default this codebase actually ran. `checkTotpCode` also logs before rethrowing now, because a verification that could not be performed being indistinguishable from a mistyped code is what kept this invisible. [packages/auth/tests/integration/totp.test.ts](packages/auth/tests/integration/totp.test.ts) grew the case that would have caught it: the suite enrolls fresh in every other test, so it only ever exercised a v13-length secret ; the new one plants a 10-byte secret directly and verifies a code against it.

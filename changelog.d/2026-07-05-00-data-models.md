- 2026-07-05: Data Models — per-field expression indexing. Fourth slice of [`@monark/data-models`](monark/app/packages/data-models) : `fields.requestIndex` / `fields.indexStatus` on `dataModelsRouter`, backed by a new `server/indexing.ts`. Provisions a type-appropriate `CREATE INDEX CONCURRENTLY` on `DataRecord` — a B-tree over the extracted-and-cast value for scalar types (`::numeric` / `::boolean` / `::timestamptz` / plain text), a GIN over the raw jsonb array for `MULTI_SELECT`/`RELATION` — scoped to the field's own Data Model via a partial `WHERE "dataModelId" = '…' AND "deletedAt" IS NULL`. `CONCURRENTLY` can't run inside a transaction and can take a while on a large table, so `requestFieldIndex` returns `"pending"` immediately and the build runs fire-and-forget in the background, tracked through the existing `DataFieldIndex` table's `status` column (`pending → building → ready`/`failed`) ; `CREATE INDEX CONCURRENTLY IF NOT EXISTS` plus a status short-circuit make repeated requests idempotent. This is v1's complete answer to "fast filtering on any admin-defined field" per the original design : the baseline GIN index (already shipped in the first migration) makes every field filterable _correctly_ from day one, speed at scale is opt-in per hot field. New integration suite (`tests/integration/indexing.test.ts`, 4 tests) verifies the actual Postgres DDL — index method via `pg_indexes.indexdef`, and a live query using the cast expression returns correct results — since none of this is meaningfully testable with a mocked client. Full pre-PR gate green.

- 2026-09-07: White-label / first run — unblocked `pnpm bootstrap` on a fresh checkout and closed the branding leaks a rebranded deploy still shipped. Found by deploying the starter from an empty worktree and retargeting it at a fictional brand end to end.

  **First run.** `pnpm bootstrap` could not run at all on a clean clone: it was launched through `tsx`, a devDependency that only exists after its own install step. It now runs under `node --experimental-strip-types` ([package.json](../package.json), [tools/bootstrap.ts](../tools/bootstrap.ts)). It also started the Supabase stack and then migrated against the blank `DATABASE_URL` it had just copied out of [packages/db/.env.example](../packages/db/.env.example), failing with a raw `execSync` stack trace; a new wiring step reads `supabase status -o env` and fills the still-blank DB URL, Supabase URL + keys, and generates the three at-rest dev secrets, so the closing "the .env files contain default test values" note is now true. The migrate step catches its own failure and prints a diagnosis. Finally, the api refused to boot on its own [services/api/.env.example](../services/api/.env.example): Node's `--env-file` parser reads an unquoted leading `#` as a comment, so `INITIAL_ORG_PRIMARY_COLOR=#2563EB` resolved to `""` and failed the hex regex that `.optional()` could not excuse. The example quotes its hex values and [env.ts](../services/api/src/lib/env.ts) treats an empty optional as unset.

  **Theming.** `BRANDING_PRIMARY` never reached the UI: `--primary`, `--ring`, `--sidebar-primary` and `--chart-1` were only overridden when the singleton org carried a `primaryColor`, so a deploy that set only the env var still rendered every button and focus ring in the starter's own colour — and `INITIAL_ORG_PRIMARY_COLOR` was missing from [deploy-checklist.md](../docs/technical-documentation/deploy-checklist.md), so following it produced exactly that. Both colour sources now feed the same token set in [layout.tsx](../services/web/src/app/layout.tsx), and `BRANDING_ACCENT` is no longer discarded the moment an org exists (which flattened every gradient to one flat colour). [globals.css](../services/web/src/app/globals.css) drops the hardcoded `#F0870C` for the neutral default, and its categorical chart ramp is rebuilt hue-neutral instead of around that orange.

  **Brand leaks.** The shipped `favicon.ico` was Monark's own butterfly mark, reachable by no env var; it is now a neutral placeholder generated from `public/logo.svg`, with Monark's kept at `public/monark-favicon.ico` for that deployment to restore. The three Supabase-rendered auth emails ([supabase/templates](../supabase/templates)) carried 22 literal "Monark" strings and 10 hardcoded `#F0870C` across the first emails any new user receives; they now ship brand-neutral with a documented wordmark insertion point, and their subjects in [config.toml](../supabase/config.toml) follow. `BRANDING_LOGO_SRC` was dead config in single-tenant deploys because the org placeholder always won ([branded-app-logo-view.tsx](../services/web/src/components/branded-app-logo-view.tsx) now prefers a configured logo over it). The Public API's OpenAPI title and its MCP tool descriptions take `BRANDING.appName`; the `mrk_` key prefix and `monark_*` tool names stay as stable identifiers.

  **Resolver.** [@monark/branding](../packages/branding/src/index.ts) looked its env up with a computed `process.env[key]`, which Next cannot inline — every field silently fell back to the neutral default in the browser, contrary to what white-label.md documented. Every variable is now a literal member access, `DEFAULT_BRANDING` and `isBrandingConfigured` are exported, and a test guards the shape.

  **Docs.** [white-label.md](../docs/technical-documentation/white-label.md) gains the auth-email section, a corrected theming model, and a retargeting checklist that names the logo format (square PNG/JPEG/WebP, not SVG) and the admin upload that actually sets it; [multi-instance.md](../docs/technical-documentation/multi-instance.md) gains a "two instances on one dev machine" section; [development.md](../docs/technical-documentation/development.md) documents `pnpm enable:dev-flags` and the `#`-quoting rule.

- 2026-09-07: Web / branding — the brand mark now resolves when the app is opened from another device on the LAN. The singleton org's `logoUrl` is stored absolute against the Supabase origin (`http://127.0.0.1:54321/...` in dev) and the sign-in page's mark is server-rendered, so the existing browser-side [dev-host-rewrite](../services/web/src/lib/dev-host-rewrite.ts) — which reads `window.location` and no-ops during SSR — never corrected it; a phone on the LAN loaded an otherwise working page with one broken image. A server-side twin, [request-host-rewrite.ts](../services/web/src/lib/request-host-rewrite.ts), swaps the hostname from the request `Host` header the same way [request-app-url.ts](../services/web/src/lib/request-app-url.ts) already does for email links, and is applied where `BrandedAppLogoData` is built ([branded-app-logo.tsx](../services/web/src/components/branded-app-logo.tsx), the [authed layout](<../services/web/src/app/(authed)/layout.tsx>)). Relation-cell avatars in [cells.tsx](../services/web/src/components/fields/cells.tsx) got the browser-side helper for the same reason. Because the server twin reads an attacker-influencable header it carries two guards the browser one doesn't need: the configured URL must itself be loopback (so a deployed origin is never relocated), and the destination must be a private host — the api's `PRIVATE_HOST_RE` shape plus link-local, CGNAT and mDNS `.local`.

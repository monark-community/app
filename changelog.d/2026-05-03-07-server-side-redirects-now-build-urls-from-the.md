- 2026-05-03: Server-side redirects now build URLs from the request's Host header instead of `request.url`. Symptom : revoking the current trusted device on a phone hitting `http://10.0.0.208:3000` bounced the user through `/auth/sign-out-stale` and ended up at `http://localhost:3000/signin` — a host the phone can't reach. Same class of bug for the TOTP-pending redirect in middleware and the half-dozen redirects out of `/auth/confirm`. Root cause : in several Next.js routing configurations (proxied prod, the `netsh portproxy` we use for LAN-from-phone testing) `request.url` reflects whatever Node sees on its loopback socket, not the public URL the browser typed.

  Fix : new [lib/request-origin.ts](monark/app/services/web/src/lib/request-origin.ts) `getRequestOrigin()` reads `X-Forwarded-Host` + `X-Forwarded-Proto` first (set by reverse proxies that terminate TLS upstream — Vercel, Cloudflare), falls back to plain `Host` + the request protocol, then to `request.nextUrl.origin` if no Host header. Used in [/auth/sign-out-stale](monark/app/services/web/src/app/auth/sign-out-stale/route.ts), every redirect in [/auth/confirm](monark/app/services/web/src/app/auth/confirm/route.ts), and the TOTP-pending redirect in [middleware.ts](monark/app/services/web/src/middleware.ts). Behaviour identical for direct production hits ; the difference only kicks in when a proxy / portproxy is in the loop.

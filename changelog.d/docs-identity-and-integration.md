- 2026-09-07: Docs: **wrote down how webhooks, secrets, API keys and service accounts relate**, the one part of the integration substrate that had no documentation at all. Three of the four had no dedicated doc (only [`secrets.md`](docs/technical-documentation/secrets.md) was complete ; webhooks had only the narrow [`webhook-secret-resolver.md`](docs/technical-documentation/webhook-secret-resolver.md), and API keys / service accounts existed only as immutable phase-3 shipped specs plus Prisma comments), and nothing anywhere explained how the four compose. New [`identity-and-integration.md`](docs/technical-documentation/identity-and-integration.md) frames them on two axes (inbound vs. outbound, credential vs. identity vs. event stream) so the whole surface fits one 2x2, with automation as the thing in the middle that is triggered by events, acts using secrets, and runs as a principal. It documents each primitive as built, a "which one do I want" decision table, and an explicit **known gaps** section: secrets are per-org only (two `secrets.manage` holders silently clobber each other, one GitHub connection per org), `ctx.getSecret` is org-scoped rather than actor-scoped, the automation actor is a nullable snapshot of the flow's author with no liveness check and no way to be a service account, webhook signing uses a second secret mechanism whose default store is in-memory (an api restart un-arms signing until each endpoint is rotated), there is no in-app environment/config concept at all, no admin visibility into human users' API keys, and the delivery worker uses raw `fetch` rather than `safeFetch`.

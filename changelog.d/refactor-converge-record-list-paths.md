- 2026-09-08: Data Models: **converged the two record-filtering implementations onto one compiler**, retiring the second execution path the docs had already flagged for removal. Record filtering had two independent implementations that had to agree: the classic filter menu's flat `fieldFilters` compiled to a structured Prisma `where` in `listDataRecords`, while the MonarkQL query bar compiled a `FilterNode` tree to raw SQL in `listDataRecordsWithQuery`. Both applied row-level role access separately, which is the part that makes a divergence an authorization bug rather than a cosmetic one, and the MQL path sits behind a default-off flag while the menu does not. New `fieldFiltersToFilterNode` in [contracts/query.ts](packages/data-models/src/contracts/query.ts) translates the legacy shape into a tree, so [records.list](packages/data-models/src/server/router.ts) now runs one path whichever front-end asked; `listDataRecords` keeps only the plain unfiltered keyset list, and its 55-line `fieldFilterWhere` implementation is gone. The automation **Find Records** node ([nodes/data.ts](packages/automation/src/server/nodes/data.ts)) moved onto the same translator, so a node predicate and a list predicate can no longer mean different things. Two semantics deliberately improved, both of which only ever match more rows: menu text matching is now case-insensitive (`string_contains` to `ILIKE`) and menu date matching is a real same-calendar-day comparison (`::date = ::date`) rather than a substring match on the stored ISO string. The 11 existing integration tests that pinned the menu semantics were kept and re-pointed through the new path, so they now prove the translation preserves behavior against real Postgres, joined by 23 new unit tests over the translator itself. No schema change, no API break: `fieldFilters` remains a valid wire input. Groundwork for MQL-scoped record permissions, which must compile into exactly one filter path to be enforceable.

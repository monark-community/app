- 2026-07-05: Data Models — `DataRecord` CRUD. Second slice of [`@monark/data-models`](monark/app/packages/data-models) (see the prior schema-management entry below) : `records.{list,getById,create,update,delete,restore}` on `dataModelsRouter`, gated by three new permissions — `data-models.record-read` / `record-write` / `record-delete` (hyphenated, not dotted — the rbac registry's key regex forbids `.` inside a key). A record's `data` payload is validated against its model's active fields via the shared `valueSchemaForField` (unknown keys stripped, matching zod's default `z.object()` behavior) ; `update` re-validates the full merged object (existing `data` overlaid with the patch), not just the patched keys, so a partial edit can't silently violate a required field. `DataRecord.title` is denormalized and recomputed on every write from the model's `titleFieldId` (falls back to `"Untitled"` when unset or empty ; `RICH_TEXT` values are stripped to plain text via the newly-exported `stripHtmlTags`, with whitespace collapsed so tag-stripping doesn't leave doubled spaces). `restore` is gated by `record-write`, matching the existing `projects.restore` / `industries.restore` convention (undoing a delete reads as an edit, not a deletion) — the schema-management phase's `models.restore` didn't need this distinction since it only has one permission tier. New `data-models.record-{created,updated,deleted}` events, carrying `dataModelKey` alongside `dataModelId` so a future subscriber (e.g. Calendar's planned materialization subscriber) can filter without a round-trip lookup. New integration suite (`tests/integration/records.test.ts`, 9 tests) covering validation, title derivation, partial-merge re-validation, slug dedup, and soft-delete/restore/hard-delete ; full pre-PR gate (`gen` + `typecheck` + `lint` + `test` + `check:tiers` + `check:modules` + `check:i18n`) green across all 18 workspace packages.

- 2026-05-07: Email + in-app alerts for permanent webhook delivery failures + endpoint auto-disable. Operators now get notified when a receiver is broken instead of having to poll the admin UI.
  - **Two new notification kinds** registered in [packages/notifications/src/server/register-core-kinds.ts](monark/app/packages/notifications/src/server/register-core-kinds.ts) :
    - `webhooks.delivery-permanently-failed` — fires when a single delivery exhausts its 5 retries (`permanent: true` on the existing `webhook.delivery-failed` event). SECURITY category, EMAIL + IN_APP, default-on, **opt-out**-able from the prefs UI since a flapping receiver could otherwise spam the inbox.
    - `webhooks.endpoint-auto-disabled` — fires when an endpoint hits 5 consecutive failures and the worker auto-disables it. SECURITY category, EMAIL + IN_APP, **`requiredEmail: true`** (cannot be opted out) — this is the actionable "your endpoint is dead" signal that operators always want.
  - **Templates** under [packages/notifications/src/templates/webhooks/](monark/app/packages/notifications/src/templates/webhooks/) — both en + fr, with subject + html + text + inapp slots. The HTML mirrors the brand chrome of existing security templates (orange CTA button, neutral table for the metadata rows, red highlight on the error reason). The CTAs link to `/admin/webhooks/<id>/deliveries` (delivery-failed) and `/admin/webhooks/<id>` (auto-disabled). Two new template vars derived in [enrich.ts](monark/app/packages/notifications/src/server/enrich.ts) : `webhookDeliveriesLink`, `webhookEndpointLink`, plus `failureLimit` from `WEBHOOK_DELIVERY_FAILURE_LIMIT`.
  - **Fan-out subscribers** in [packages/notifications/src/server/subscribers/index.ts](monark/app/packages/notifications/src/server/subscribers/index.ts) :
    - `webhook.delivery-failed` (with `permanent: true` filter) → fan out to org admins (org-scoped endpoint) or sysadmins (platform-tier endpoint).
    - `webhook.endpoint-disabled-after-failures` → same fan-out.
    - The dispatcher's existing 60s dedupe window collapses near-simultaneous failures of the same delivery so a synchronized retry cluster doesn't double-send.
  - **`organizationId` + `endpointUrl` on delivery events** ([packages/webhooks/src/contracts/events.ts](monark/app/packages/webhooks/src/contracts/events.ts)). Added to `WebhookDeliverySucceededEvent` and `WebhookDeliveryFailedEvent` so subscribers can route to the right operator group + render the URL in the email without an extra DB roundtrip per event. The worker populates both from the existing `delivery.endpoint` join.
  - **Two new rbac data helpers** ([packages/rbac/src/server/data.ts](monark/app/packages/rbac/src/server/data.ts)) : `listOrgAdminUserIds(orgId)` returns the active built-in `ADMIN` holders for one org ; `listSysadminUserIds()` returns the active platform-tier `SYSADMIN` holders. Returns user ids only — caller hydrates User rows themselves. Re-exported from `@monark/rbac/server`.
  - **Dependency**: `@monark/notifications` now depends on `@monark/webhooks` (for the event type imports + `WEBHOOK_DELIVERY_FAILURE_LIMIT` constant). Direction is one-way ; webhooks doesn't depend on notifications, no cycle.
  - **Effect.** A webhook receiver that's been down long enough to exhaust retries on a delivery generates one email per qualifying admin, plus a follow-up "endpoint auto-disabled" email when the consecutive-failure cap hits. Admins recover by fixing the receiver and re-enabling the endpoint from `/admin/webhooks/<id>` ; the failure counter resets on the next successful delivery.
  - `pnpm typecheck` stays clean across all 15 packages.

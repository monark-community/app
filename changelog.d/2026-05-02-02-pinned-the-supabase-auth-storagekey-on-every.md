- 2026-05-02: Pinned the Supabase auth `storageKey` on every client so the dev-host URL rewrite can't desync sessions. Symptom : LAN-from-phone testing shows `/dev-diagnostics` all-green (web, api, Supabase reachable from phone) but `/account` still loads with empty fields + spinner-locked queries because the browser-side Supabase client can't find the session cookie. Root cause : `supabase-js` defaults `auth.storageKey` to a value derived from the project URL ; the [dev-host-rewrite](monark/app/services/web/src/lib/dev-host-rewrite.ts) changes the URL on the browser (loopback → LAN host) but NOT on the server, so the server writes `sb-127.0.0.1-auth-token` and the browser looks under `sb-10.0.0.208-auth-token`, finds nothing, fires every tRPC call as anonymous, every authed query returns empty.

  Fix : new [lib/supabase/storage-key.ts](monark/app/services/web/src/lib/supabase/storage-key.ts) exporting a single constant (`sb-app-auth-token`, overridable via `NEXT_PUBLIC_AUTH_STORAGE_KEY`) that's now pinned on the [server client](monark/app/services/web/src/lib/supabase/server.ts), the [browser client](monark/app/services/web/src/lib/supabase/browser.ts), AND the [middleware client](monark/app/services/web/src/middleware.ts). All three sides now read + write under the same name regardless of which URL each one is configured with.

  `/dev-diagnostics` extended : new "Auth state on this device" panel shows the cookies the browser can see (names only), whether `getSession()` returned a session, the resolved user id, and the result of an authed `users.me` tRPC call. Surfaces "reachable but no session" vs "session valid but tRPC rejected" vs "everything works but data still empty" — the three different shapes of "data not loading" the previous diagnostic couldn't disambiguate.

  Existing devs : sign out + sign back in once after the upgrade ; old cookies under the URL-derived key won't migrate automatically. Production unaffected (URLs aren't loopback there, no rewrite, key would have been stable anyway).

- 2026-07-05: Data Models — new core module, schema management phase. Added [`@monark/data-models`](monark/app/packages/data-models) (core tier, [modules.manifest.ts](monark/app/modules.manifest.ts)), the first slice of the polymorphic "Data Model" engine described in [docs/features-planning/phase-2/polymorphic-db.md](monark/app/docs/features-planning/phase-2/polymorphic-db.md). Prisma models `DataModel` / `DataField` / `DataRecord` / `DataModelIntegration` / `DataFieldIndex` under a new `// ── MODULE: data-models ──` banner ([schema.prisma](monark/app/packages/db/prisma/schema.prisma), migration `20260706000312_add_data_models`, hand-augmented with two NULL-aware partial-unique indexes — `DataModel` keys are unique per-org or globally when platform-wide — plus a baseline GIN index on `DataRecord.data`). This phase ships `DataModel` + `DataField` CRUD only (`dataModelsRouter` at `trpc.dataModels.{models,fields}.*`), gated by new `data-models.manage-schema` / `read-schema` permissions ; `DataRecord` CRUD and the module-integration registry land in later phases. The field-type validation logic that used to live only in [`services/web/src/components/fields/schema.ts`](<monark/app/services/web/src/app/(authed)>) is now shared : [`valueSchemaFor`](monark/app/packages/data-models/src/contracts/field-types.ts) in `@monark/data-models/contracts` builds the structural zod fragment for a field's value from its type + config, and the client's `schemaFor` is now a thin adapter onto it — one implementation instead of two hand-synced ones, verified by the existing 23-test `fields.test.ts` suite passing unchanged. New integration suite (`packages/data-models/tests/integration/data.test.ts`, 9 tests) locks in the partial-unique-index behavior against a real Postgres testcontainer. `registerDataModelsPermissions()` / `registerDataModelsEventTypes()` wired into [server.ts](monark/app/services/api/src/server.ts). `tsc` + `eslint` + `check:tiers` + `check:modules` green.

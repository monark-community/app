- 2026-09-10: Documentation — **re-baselined the features-planning folder against what actually shipped, and specced the next five programs**. The folder had drifted into a single `proposed/` pile that mixed a live backlog with three features that had already landed, so [wiki.md](docs/features-planning/shipped/wiki.md), [block-editor.md](docs/features-planning/shipped/block-editor.md) and [global-search.md](docs/features-planning/shipped/global-search.md) moved to a new `shipped/` folder ; a spec that has landed is a historical record and must stop being editable, which is the same rule the `phase-*` folders already follow. The [README](docs/features-planning/README.md) is rewritten around an **active-programs table** rather than the abandoned phase-0-to-3 roadmap, and closes out white-labelling, social sign-in, the documentation platform at [docs.app.monark.io](https://docs.app.monark.io) and the single-tenancy decision, each linked to the technical doc that now owns it. It also records a deliberate reversal worth flagging rather than burying: [`phase-3/data-models-visualizations.md`](docs/features-planning/phase-3/data-models-visualizations.md) concluded that Calendar and Kanban should stay separate tabled modules, and the new plan makes them view kinds over Data Models ; the evidence changed (the single query compiler, saved views and record scopes all landed since), so the old spec stays unedited and the README says why.

  Five new specs. [workspace-unification.md](docs/features-planning/proposed/workspace-unification.md) merges `/data`, `/wiki`, `/kanban` and `/calendar` into one `/workspace` section over one nested tree, and settles the load-bearing question the whole program turns on: the tree cannot live in `@monark/wiki`, because the tier walls forbid core depending on extended, so it becomes a new **core** `@monark/workspace` owning tree shape only, with node kinds registered the way search sources and automation nodes already are. [views-system.md](docs/features-planning/proposed/views-system.md) grows `DataRecordView` into a `TABLE` / `BOARD` / `CALENDAR` view entity with server-side presentation config, absorbs `KanbanView`, and migrates boards and calendars onto Data Models while leaving reminders in a calendar-owned sidecar rather than bloating every model. [access-control-console.md](docs/features-planning/proposed/access-control-console.md) covers the half of the record-scope work that is not built: the engine shipped on `2026-09-08`, but access is still authored in four places, three of which are the sections the workspace program deletes. [integrations-rework.md](docs/features-planning/proposed/integrations-rework.md) introduces a `Connection` so a flow can call an authenticated API without a module, and makes "a secret value never leaves a node" structural via a branded `SecretValue` instead of a comment in `registry.ts` ; it folds in four open items from the `2026-07-29` security audit. [deploy-pipeline-completion.md](docs/features-planning/proposed/deploy-pipeline-completion.md) and [dev-overlay-flag-tree.md](docs/features-planning/proposed/dev-overlay-flag-tree.md) are the two small ones.

  Two live findings came out of the audit and are recorded in [backlog.md](docs/todo/backlog.md) rather than only in a spec, because they are current defects and not future work: every Render service still carries `autoDeploy: true`, so each merge deploys twice, once ungated on push and once on green, which is the exact failure [deploy-api.yml](.github/workflows/deploy-api.yml) was built to close ; and the web half is not gated on green at all, since Vercel still deploys `develop` and `main` from its own git integration. The otplib 12-to-13 item is closed with the two follow-up fixes it needed, and with the reason its test suite missed the lockout: every TOTP test enrolled fresh, so nothing ever exercised a v12-length secret.

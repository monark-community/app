- 2026-09-10: Documentation — **the integration program is now written down in the repo, and the features-planning folder is re-baselined against what actually shipped**. The program was approved on 2026-09-07 with product decisions locked on 2026-09-08, but it lived only in a session plan file outside the repository ; a machine reboot losing that context is exactly the failure mode a repo-tracked spec prevents. Five specs under [features-planning/proposed](docs/features-planning/proposed/) now carry it, phase by phase, re-verified against the code: [access-control-console.md](docs/features-planning/proposed/access-control-console.md) (Phase A, whose engine already shipped on `2026-09-08`, leaving the authoring surface), [views-system.md](docs/features-planning/proposed/views-system.md) (Phase B, a real View entity with `type` + `config`, and the sort input on `records.list` that is the one genuine engine gap), [workspace-unification.md](docs/features-planning/proposed/workspace-unification.md) (Phase C, one core `ContentNode` tree under a `/workspace` section), [automation-model-refs.md](docs/features-planning/proposed/automation-model-refs.md) (Phase D, a reverse index of which models an automation touches) and [integrations-rework.md](docs/features-planning/proposed/integrations-rework.md) (Phase E, configuration variables, per-user credentials, the automation actor as a live principal, one integrations home). Each spec marks its **locked decisions** as not-to-be-re-opened, which is the property that makes a written plan worth more than a remembered one.

  Two decisions were re-confirmed against a contradictory reading and are recorded rather than left implicit. **Kanban and Calendar materialize and write back ; they do not migrate.** `KanbanCard` and `CalendarEvent` stay authoritative, a database-backed view materializes `DataRecord`s into them through a subscriber, and a drag writes back to the mapped field. The alternative (migrate records into Data Models and drop the typed tables) was considered and rejected again, so `KanbanView` stays untouched for native boards and `DataRecord.position` is deliberately **not** added, because drag ordering already works in `KanbanCard.position`. **The old routes are deleted, not redirected**: `/data`, `/wiki` and `/kanban` go with no shim, which makes re-pointing every server-built `registerSearchSource` href, notification template and stored automation-node link part of C4 rather than a follow-up, and means external bookmarks 404 ; that cost is now stated in the spec instead of discovered in support. Calendar keeps its own top-level entry and is _also_ a view type, the way Notion does. One decision was deliberately reversed by the operator and is flagged inside the spec that carries it: plan section A.8 had per-record sharing staying on the record, and access authoring now consolidates into the admin section, with only a read-only summary left on the object.

  Folder hygiene alongside it. The [README](docs/features-planning/README.md) is rewritten around the program's phases and sequencing rather than the abandoned phase-0-to-3 roadmap, and closes out white-labelling, social sign-in, the documentation platform and single-tenancy. It also corrects, without editing it, the one shipped spec that is still partly live: [`data-models-visualizations.md`](docs/features-planning/phase-3/data-models-visualizations.md)'s verdict was re-confirmed and its Part B is the still-unbuilt Phase C5, but two blockers it cited ("no range operators", "schema fragments don't exist") have both shipped since.

The otplib 12-to-13 item is closed with the two follow-up fixes it needed, and with the reason its suite missed the lockout: every TOTP test enrolled fresh, so nothing ever exercised a v12-length secret.

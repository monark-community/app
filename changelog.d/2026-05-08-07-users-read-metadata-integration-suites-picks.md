- 2026-05-08: Users `read` + `metadata` integration suites. Picks up the second-lowest-coverage package on the merged baseline (34 % lines → 81 % lines) by closing the read-wrapper + per-user metadata gaps that the existing `data.test.ts` didn't reach. Floor bumped from 25 → 75 in [tools/merge-coverage.ts](monark/app/tools/merge-coverage.ts).
  - **`@monark/users` read wrappers** ([packages/users/tests/integration/read.test.ts](monark/app/packages/users/tests/integration/read.test.ts)). 9 cases. The `read.ts` exports are thin wrappers over `data.ts` finders, but two of them carry branches worth pinning : `getByIdOrThrow` raises `NotFoundError` on a missing id (the canonical error every router-level handler unwraps to a 404), and `getCurrent` short-circuits to `null` when `ctx.userId` is itself null (the unauthenticated-request branch most server actions guard on first thing). Plus `getById` / `getByEmail` round-trips so the data-layer pass-through is locked in.
  - **`@monark/users` metadata** ([packages/users/tests/integration/metadata.test.ts](monark/app/packages/users/tests/integration/metadata.test.ts)). 20 cases against the testcontainer covering the per-user metadata API end-to-end. Buckets : (1) `setUserMetadataValue` create + upsert + arbitrary JSON-shaped values (object / array / number) so the `Json` column round-trips correctly. (2) `getUserMetadataValue` returns `undefined` for missing tuples, the stored value for real rows, and crucially does NOT leak across users for the same `(module, key)`. (3) `listUserMetadataForModule` returns rows for one user × one module sorted by key, excludes other-module rows, returns empty for users with no metadata. (4) `deleteUserMetadataValue` removes by tuple + is idempotent on missing rows (no throw). (5) `deleteUserMetadataForModule` returns `{ count }`, doesn't touch other modules' rows or other users' rows — both the cross-module and cross-user isolation guarantees are explicit specs because the `deleteMany` `WHERE` shape is the kind of code that can pass typecheck and silently drop the wrong rows. (6) Validation — invalid module names, empty / oversized / pattern-violating keys all reject with `ValidationError`, with separate cases pinning that the read paths (`listUserMetadataForModule`, `getUserMetadataValue`) validate too (callers expect rejection at the boundary, not silently-empty results).
  - **Net effect.** `src/server/read.ts` lifts from 0 % → 100 % covered ; `src/server/metadata.ts` lifts from 0 % → near-100 %. Package floor bumps from `25/25/55/75` to `75/75/85/85`. The `event-types.ts` + `permissions.ts` registration shims are still at 0 % (called once at api boot, not exercised by any spec) ; covering them would push the floor higher but adds little signal because they're table-driven `register*()` calls.

- 2026-05-29: User-configurable trusted-device window + one-click revoke from email. Two security-UX upgrades to the trusted-device flow that land together because they share the new-device-email surface.
  - **Configurable trust window.** New `User.trustedDeviceTtlDays` column (default 90 days) lets each user pick 30 / 60 / 90 days from `/account/security`. The RFC 6265bis 400-day cookie ceiling is still enforced at write-time via `clampDeviceTtlDays` but isn't offered in the UI — 90 days is plenty for most active users, longer than that drifts past the point where "did I trust this device on purpose?" stops being a meaningful question. Migration [20260529180000_add_trusted_device_ttl_days](monark/app/packages/db/prisma/migrations/20260529180000_add_trusted_device_ttl_days/migration.sql) ; backend reads it in [`recognizeOrRegister`](monark/app/packages/auth/src/server/trusted-devices.ts) and returns the effective TTL alongside the cookie value so [`recognizeDeviceAfterAuth`](monark/app/services/web/src/lib/trusted-device-cookie.ts) sets the cookie's `Max-Age` to match the row's `expiresAt`. New tRPC mutation `users.updateTrustedDeviceTtl` retroactively slides every active device's `expiresAt` forward by the new TTL from `lastSeenAt` so "tighten my window" takes effect immediately. UI Select wired into [TrustedDevicesSection](<monark/app/services/web/src/app/(authed)/account/trusted-devices-section.tsx>) above the device list, with i18n strings in both locales. The 400-day ceiling mirrors RFC 6265bis' cookie `Max-Age` cap — anything higher would be silently truncated by the browser.
  - **One-click revoke link in new-device emails.** The "If that wasn't you, revoke this device" CTA in `auth.new-device` no longer dumps the user on `/account/security` to hunt for the right row — it now lands on `/auth/revoke-device/<token>` which revokes the specific device with one click. Token is an HMAC over `{ purpose, userId, deviceId, expiresUnixSec }` signed by the new `EMAIL_ACTION_SECRET` env var (32-char dev default with a `logger.warn` ; production must override). Helper lives at [packages/auth/src/server/email-action-token.ts](monark/app/packages/auth/src/server/email-action-token.ts) with constant-time signature compare. New publicProcedure [`auth.trustedDevices.revokeByEmailToken`](monark/app/packages/auth/src/server/index.ts) verifies the token + revokes ; the action is idempotent so a second click on the same link is a no-op. Web page at [services/web/src/app/auth/revoke-device/[token]/](monark/app/services/web/src/app/auth/revoke-device/[token]/) deliberately renders a confirm button instead of firing on page load — link-prefetchers (email-scanner bots, browser "preload on hover") would otherwise revoke before the human clicks. Token data shape declared in the notification registry for `auth.new-device` so the subscriber-injected `revokeLink` overrides `globalVars()`'s generic `/account/security` link only for this kind.
  - **Backlog items filed in [docs/todo/backlog.md § Trusted devices](monark/app/docs/todo/backlog.md#trusted-devices)** : step-up auth on sensitive actions during the first 24h after a new-device sign-in (mitigates password-only users), out-of-band approval flow (banks pattern, high-friction), and per-IP rate-limit on the revoke endpoint.

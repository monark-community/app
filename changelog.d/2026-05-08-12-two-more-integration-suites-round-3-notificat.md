- 2026-05-08: Two more integration suites (round 3). Notification subscribers (the cross-module wiring layer) and feature-flag scoped resolution (the runtime-decision layer) now have direct CI gates instead of being implicitly tested by surrounding suites.
  - **`@monark/notifications` subscribers** ([packages/notifications/tests/integration/subscribers.test.ts](monark/app/packages/notifications/tests/integration/subscribers.test.ts)). 14 cases covering every domain event the subscribers bind to. Mocks `notify` at the module-import boundary via `vi.mock("../../src/server/dispatch", …)` so the spec focuses on the wiring contract — each event maps to the right notification kind, the right recipient(s), and the right data shape — without re-testing the dispatch path (which has its own integration suite). Covers : the auth events (`trusted-device.added` → `auth.new-device` with the device row joined in, plus the silent fall-through when the row's gone ; `user.password-changed`, `totp.enabled`, `totp.disabled`, `trusted-devices.all-revoked`) ; the account-lifecycle events (`user.email-changed`, `user.deletion-requested`, `user.deletion-canceled`) ; the webhook operator alerts (org-scoped permanent failures fan out to org admins with `scope: "org"`, platform-tier permanent failures fan out to sysadmins with `scope: "platform"`, transient failures stay silent because `permanent === false`, the `endpoint-disabled-after-failures` event looks up the URL and falls back to a sentinel when the row's already gone). Plus the registration-idempotency guard : calling `registerNotificationSubscribers()` twice doesn't double-bind handlers (would cause every event to fire each subscriber twice). New `_resetSubscribersForTesting` helper exported from `@monark/notifications/server` so the `beforeEach` can re-bind from scratch.
  - **`@monark/feature-flags` is-enabled / getFlags integration** ([packages/feature-flags/tests/integration/is-enabled.test.ts](monark/app/packages/feature-flags/tests/integration/is-enabled.test.ts) + [packages/feature-flags/vitest.integration.config.ts](monark/app/packages/feature-flags/vitest.integration.config.ts)). 12 cases against a Postgres testcontainer covering the scoped-precedence resolution end-to-end (the `mostSpecific` pure function had unit coverage already ; this locks in that the SQL `WHERE` shape returns exactly the rows the resolver expects). Three buckets : (1) registry default fallback (off-by-default + on-by-default + unknown-flag fallthrough), (2) global override beats default in both directions, (3) scoped precedence — user-scoped beats org/role/global, org-scoped beats global with no user override, user-scoped doesn't leak across users, org-scoped doesn't leak across orgs. Also covers `getFlags` multi-key batching, the empty-key short-circuit, and the `(module, flagKey) → FeatureFlag` FK cascade so removing a flag definition cleans up its overrides automatically. New `vitest.integration.config.ts` + `@monark/test-utils` workspace devDep + `test:integration` script ; the package now participates in the CI verify job's `test:integration` step.
  - **Net effect.** Notifications subscribers are the seam between every module's domain events and the user-facing inbox + email pipeline ; a regression there would silently swallow a security alert. Feature-flag scoped resolution is the seam every runtime decision (enable / disable / variant pick) routes through ; a regression there could silently flip a critical-path flag for the wrong scope. Both surfaces now break the build before they reach staging.

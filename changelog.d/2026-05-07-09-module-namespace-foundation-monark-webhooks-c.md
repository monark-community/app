- 2026-05-07: Module-namespace foundation + `@monark/webhooks` core module. Five-phase rollout that opens core to extension by non-core modules without modifying core code, plus a generic webhook delivery system over the same event bus.
  - **Phase 1 — Module-namespace foundation.** Feature flags + RBAC permissions + notification kinds were each closed registries (`const FLAGS`, `const PERMISSIONS`, `const NOTIFICATION_KINDS`) where adding an entry meant editing a core file. Now they're runtime registries any module registers into at api boot.
    - Migration [20260507100000_add_module_to_flags_and_permissions](monark/app/packages/db/prisma/migrations/20260507100000_add_module_to_flags_and_permissions/migration.sql) adds a `module` column to `FeatureFlag`, `FeatureFlagOverride`, and `RolePermission`. Primary key on `FeatureFlag` becomes `(module, key)` ; uniqueness on `RolePermission` becomes `(roleId, module, permission)`. Backfill : `auth.*` flags get `module='auth'`, `tenancy.*` get `module='tenancy'` ; permission slugs lose their colon prefix (`org:update-settings` → `update-settings`), with the module derived from the prefix mapping (`org:` → `organizations` for the orgs-owned set + `rbac` for the rbac-owned set, etc.).
    - [packages/feature-flags/src/contracts/flags.ts](monark/app/packages/feature-flags/src/contracts/flags.ts) replaces the static `FLAGS` const with `registerFlags(module, flags)` + `isKnownFlag(dotted)` + `parseFlagKey(dotted)` + `listFlagDescriptors()`. Call sites still use the dotted form `"<module>.<key>"` ergonomically ; internal resolution parses to the (module, key) pair.
    - [packages/rbac/src/contracts/permissions.ts](monark/app/packages/rbac/src/contracts/permissions.ts) does the same for permissions ; `validatePermissionList` now returns parsed `{ module, key }[]` pairs, `hasPermission` / `requirePermission` accept the dotted form. Categories become loose strings so an extended module can introduce its own grouping.
    - Each owning module ships a `register<Module>FeatureFlags()` / `register<Module>Permissions()` helper. [services/api/src/server.ts](monark/app/services/api/src/server.ts) calls them in deterministic order at boot, before `syncFlagsToDatabase()`.
  - **Phase 2 — Notification kinds runtime registry.** [packages/notifications/src/contracts/registry.ts](monark/app/packages/notifications/src/contracts/registry.ts) drops the static `NOTIFICATION_KINDS` const + `TEMPLATES` map for `registerNotificationKind(kind, def, messages)`. The `NotificationDataRegistry` interface stays typed via TypeScript declaration merging so per-kind payloads remain checked at call sites. `registerCoreNotificationKinds()` registers the existing eight kinds (auth._ + account._) at api boot ; extended modules register their own with the same API.
  - **Phase 3 — User / Organization metadata sidecar.** Migration [20260507110000_add_user_org_metadata_sidecar](monark/app/packages/db/prisma/migrations/20260507110000_add_user_org_metadata_sidecar/migration.sql) adds `UserMetadata` + `OrganizationMetadata` tables keyed on `(parent_id, module, key)` with a `Json` value. Generic CRUD lives under `users.metadata.{list,get,set,delete}` and `organizations.metadata.{list,get,set,delete}` tRPC procedures, gated by `users.read-metadata-for-module-<x>` / `users.write-metadata-for-module-<x>` (and the orgs equivalent) permissions that an extended module registers itself. Lets a future `@monark/posts` attach per-user preferences without touching the core schema.
  - **Phase 4 — `@monark/webhooks` core module.** Operator-registered HTTP endpoints that receive a fan-out of every domain event the platform emits. Schema in migration [20260507120000_add_webhooks](monark/app/packages/db/prisma/migrations/20260507120000_add_webhooks/migration.sql) : `WebhookEndpoint` (URL + secretHash + status + per-org or platform scope), `WebhookSubscription` (event-type filter, exact or prefix), `WebhookDelivery` (the outbox row, idempotency-keyed), `WebhookDeliveryAttempt` (per-attempt audit). The wildcard subscriber listens on the new bus `*` channel ([packages/common/src/events.ts](monark/app/packages/common/src/events.ts)) so any module's events route through webhooks the moment they're in the manifest. The worker signs the body with HMAC-SHA-256 (`Webhook-Signature: v1=<hex>`), POSTs with a 10s timeout, retries with exponential backoff (5 attempts, 30s base, 6h cap), and auto-disables endpoints after 5 consecutive failures. `webhooksRouter` exposes endpoint CRUD + secret rotation + delivery inspection + manual retry under `webhooks.*` ; `/cron/sweep-webhook-deliveries` is the external fallback for the in-process worker. The admin UI on top of this surface is a deferred follow-up — tracked in [packages/webhooks/README.md](monark/app/packages/webhooks/README.md#deferred-follow-ups).
  - **Phase 5 — Documentation.** New [docs/technical-documentation/extensibility-contract.md](monark/app/docs/technical-documentation/extensibility-contract.md) codifies what core guarantees to extended modules and what extended modules must never touch. Per-module READMEs updated to reflect the runtime registries. Manifest gains `@monark/webhooks` at tier `core`.
  - **Workspace effect.** Three new migrations, one new core package (`@monark/webhooks`), one new schema column on three existing tables, one new wildcard channel on the event bus, six new permission slugs registered at boot. Migration is non-destructive — every existing row survives, FK and unique constraints widen rather than tighten. The `services/api` boot sequence gains five `register*` calls + the webhook worker + the cron sweep endpoint.
  - **Operator handoff** : `pnpm install`. `pnpm --filter @monark/db db:migrate:dev` to apply the three migrations in order. `pnpm gen` to regenerate `events.generated.ts` (already updated for `@monark/webhooks`) and the app router composition. `pnpm --filter api dev` and check the boot log for the new `webhook delivery worker started` line. The webhook secret resolver MUST be set via `setWebhookSecretResolver()` before the worker can sign requests — see [docs/technical-documentation/webhook-secret-resolver.md](docs/technical-documentation/webhook-secret-resolver.md) for three concrete backing-store recipes (env-var JSON, per-endpoint env vars, AWS Secrets Manager / Vault) ; until one is wired, every delivery records a "no plaintext secret available" error and the endpoint auto-disables after 5 consecutive failures.
  - **Codegen tools tolerate config-only modules.** `tools/gen-events.ts` and `tools/gen-routers.ts` previously aborted when a manifest module lacked `contracts/events.ts` or `server/index.ts` ; they now skip those modules silently. Lets `@monark/branding` (constants-only) live in the manifest for the tier check without forcing it to ship empty event / router stubs.

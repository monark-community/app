- 2026-09-08: Deployment — the api now deploys on green, and the cron services declare `autoDeploy` like the api already did. Render's native trigger fires on **push** rather than on a passing build, so a merge that breaks CI still deployed ; worse, it was invisible from this repo, leaving nothing to look at when the backend failed to follow a merge that the Vercel-hosted web side had already picked up. [deploy-api.yml](.github/workflows/deploy-api.yml) keys on `workflow_run` for the CI workflow, deploys only when `conclusion == success`, resolves the Render services **by name** from [render.yaml](render.yaml)'s convention rather than per-service id secrets (so it needs exactly one secret, `RENDER_API_KEY`, and adding a service to the blueprint doesn't mean adding another), and polls each deploy to a terminal state so the check reflects the deploy's real outcome instead of "we asked Render to deploy". Absent the secret it no-ops with a notice rather than failing, so a fork never sees a red X for a deploy it was never going to run. Separately, the four cron services had no `autoDeploy` at all — whether they picked up a push depended on a dashboard default rather than the blueprint, meaning the scheduled jobs could keep running stale code against a freshly deployed api. [environments.md](docs/technical-documentation/environments.md) documents the setup and the "backend didn't follow a merge" diagnosis path.

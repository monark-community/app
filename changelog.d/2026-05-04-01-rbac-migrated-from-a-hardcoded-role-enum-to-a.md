- 2026-05-04: RBAC migrated from a hardcoded `Role` enum to a flexible `Role` + `RolePermission` table-driven model. Operators can now create, edit, and delete custom org-scoped roles via [/admin/rbac](<monark/app/services/web/src/app/(authed)/admin/rbac/page.tsx>) — name, description, and a permission set picked from a category-grouped matrix. Multi-role-per-user was already supported by `RoleAssignment` ; the UI now surfaces it through the existing /admin/users/[id] role picker (extended to read from the per-org role list). The previous enum's `MONARK_ADMIN` collapsed into the single built-in `ADMIN` row : it lives in the `Role` table with `builtIn: true, organizationId: null`, `key` and `builtIn` are immutable from the API, deletion is hard-blocked, and `hasPermission` short-circuits to `true` for any active ADMIN assignment regardless of `RolePermission` rows so new permissions added to the system later are auto-granted. The `DEVELOPER`, `AMBASSADOR`, `STUDENT` enum values were dropped (they were Monark-specific and the user wants every role beyond `ADMIN` to be operator-defined per org). Schema migration at [packages/db/prisma/migrations/20260504170000_rbac_table_driven_roles](monark/app/packages/db/prisma/migrations/20260504170000_rbac_table_driven_roles/migration.sql) is destructive on populated DBs (drops assignments / invites / flag-overrides for the retired enum values, repoints `MONARK_ADMIN` + `ADMIN` rows at the new ADMIN row) ; user explicitly approved for the starter codebase. Inside the migration, the `Organization → RoleAssignment` `ON DELETE CASCADE` is preserved so the "deleted org / null orgId / accidental platform admin" path still can't happen. The `@monark/rbac` package was rewritten end-to-end : new helpers `hasRoleKey` (replaces enum-based `hasRole`), `requireRoleKey` (replaces `requireRole`), `getAllAssignments` now joins the role row, `findRoleById` / `findBuiltInAdminRole` / `listRolesForOrg` exposed for callers, plus the new write helpers `createRole` / `updateRole` / `deleteRole` (which validate role key shape, reserve the `ADMIN` key, and refuse deletion when assignments exist). New tRPC procedures on the rbac router : `adminListRoles`, `adminCreateRole`, `adminUpdateRole`, `adminDeleteRole`, `adminListPermissions` ; existing `adminAssignRole` / `adminRevokeRole` switched from enum to roleId input. Consumer packages updated to match : `Invite.role` enum → `Invite.roleId` FK ; `FeatureFlagOverride.role` enum → `FeatureFlagOverride.roleId` (still nullable for the global / org / user override variants) ; `FlagScope` carries `roleId` instead of `role` ; `users.adminListUsers` and `organizations.invites.adminListAll` now filter by `roleIds`. Web UI followed : `/admin/users/[id]` Roles card, the user-list role filter, and the invite dialog all read available roles from the live tRPC query against the org's role list (built-in + custom). New events : `rbac.role-created`, `rbac.role-updated`, `rbac.role-deleted`. Permission registry trimmed in [packages/rbac/src/contracts/permissions.ts](monark/app/packages/rbac/src/contracts/permissions.ts) : Monark-specific permissions (`voting:*`, `onboarding:*`, `contributions:*`, `referral:*`) removed ; permissions now carry `description` + `category` so the UI matrix renders without hardcoding. New `rbac:manage-roles` permission added for the new role-CRUD surface. **i18n** (en + fr) : new `admin.rbac.manager.*` and `admin.rbac.editor.*` keys covering the role list, the create/edit dialog, and the four permission categories. **Awaiting** : the operator runs `pnpm --filter @monark/db exec prisma generate` (after stopping any dev server holding the Windows DLL lock) + applies the migration via `prisma migrate dev` on a fresh dev DB.

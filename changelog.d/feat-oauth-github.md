- 2026-09-08: Added social sign-in to `@monark/auth`, with GitHub as the first provider; a "Continue with GitHub" button on [/signin](<services/web/src/app/(anon)/signin/page.tsx>) + [/signup](<services/web/src/app/(anon)/signup/page.tsx>) driven by the anon-safe `auth.oauth.providers` query, a [/auth/callback](services/web/src/app/auth/callback/route.ts) route that trades the PKCE code for a session, and [`provisionOAuthUser`](packages/auth/src/server/oauth.ts) which creates the shadow `User` row Supabase never told us about (idempotent, re-reads identity from the Supabase admin API rather than trusting the caller, emits `user.signed-up` with the new `provider` field). A provider-verified email is required (`email-unverified` refusal) and an address already owned by another `User` row is refused case-insensitively (`email-collision`); both surface as banners on /signin. Accounts with no password get a "Set a password" variant of the security card ([`setPasswordAction`](<services/web/src/app/(authed)/account/actions.ts>), which refuses once a password exists), and email change defers until a password exists. Configured per deployment through the api's `AUTH_OAUTH_PROVIDERS` env plus the `[auth.external.github]` stanza in [supabase/config.toml](supabase/config.toml) (shipped disabled), behind the `auth.oauth` kill-switch flag. Verified end to end against a real GitHub OAuth app.
- 2026-09-08: Closed a two-factor gap on the email-confirmation path. Password sign-in, social sign-in and [/auth/confirm](services/web/src/app/auth/confirm/route.ts) now all converge on [`completeSignIn`](services/web/src/lib/complete-sign-in.ts); the confirm route previously ran a shorter tail of its own, so confirming an email established a session without ever challenging an enrolled authenticator. It now stamps `emailVerifiedAt` and then delegates, picking up the TOTP gate, `user.signed-in` and the deletion-grace bounce with it.
- 2026-09-08: Connected accounts on `/account/security` became read-write. Providers can be connected ([`beginProviderLinkAction`](<services/web/src/app/(authed)/account/actions.ts>) + `supabase.auth.linkIdentity`) and disconnected ([`unlinkProviderAction`](<services/web/src/app/(authed)/account/actions.ts>)), with [`assertCanUnlinkProvider`](packages/auth/src/server/oauth.ts) refusing to remove the last usable sign-in method and a TOTP code required when enrolled — the same treatment password and email changes get, because removing a way into an account is at least as sensitive as changing one. Both emit domain events (`oauth.provider-linked` / `oauth.provider-unlinked`, the latter carrying the post-change `remainingProviders` + `hasPassword`). A link round trip returns to the same callback as a sign-in but must skip the TOTP gate the existing session already cleared; that distinction rides on a single-use HTTP-only cookie ([`oauth-link-cookie.ts`](services/web/src/lib/oauth-link-cookie.ts)) rather than a URL parameter, which would have handed an attacker a documented way to skip their own second factor.
- 2026-09-08: Added a one-time two-factor enrollment nudge after email verification ([`TotpOnboardingPrompt`](services/web/src/components/totp-onboarding-prompt.tsx)), mounted beside the recovery-code reminder. Dismissal is permanent and lives in the user-metadata sidecar rather than a schema column. Behind the new `auth.totp-onboarding-prompt` flag (default on): enabling it on an existing deployment shows the nudge once to every not-yet-enrolled user, so it is a deliberate operator decision rather than a silent rollout.

- 2026-05-01: Forgot-password flow. New `/forgot-password` page (under `(anon)`) takes an email + calls [`requestPasswordResetAction`](<monark/app/services/web/src/app/(anon)/forgot-password/actions.ts>) which delegates to `supabase.auth.resetPasswordForEmail` ; the action always returns ok regardless of whether the address matches a real account so the form can't be used as an enumeration oracle. The recovery link sets `redirectTo=${appUrl}/auth/confirm?type=recovery` which the existing [auth/confirm route](monark/app/services/web/src/app/auth/confirm/route.ts) now special-cases (both the token-hash and the post-verify no-token paths) by forwarding to a new `/auth/reset-password` page. Reset page lives outside `(authed)` on purpose — the recovery-flow session has no trusted-device cookie and the (authed) gate would bounce it through `/auth/sign-out-stale` before the user could finish. New [`resetPasswordAction`](monark/app/services/web/src/app/auth/reset-password/actions.ts) runs the new password through the same `auth.checkPassword` (offline rules + HIBP) used by signup + the in-account change, calls `updateUser({ password })`, fires `notifyPasswordChanged({ triggeredBy: "reset" })` so the security email goes out, then signs the user out and redirects to `/signin?passwordReset=1`. The signin page surfaces a confirmation banner via [SignInStatusBanner](<monark/app/services/web/src/app/(anon)/signin/signin-status-banner.tsx>) on that query param. Signin form gains a "Forgot password?" link aligned with the password label, sized as a small caption to keep the layout balanced. **i18n** (en + fr): new `auth.{forgotPassword.{title, subtitle, labels.email, submit, submitting, sentTitle, sentBody, backToSignIn, signInLink}, resetPassword.{title, subtitle, labels.{new, confirm}, submit, submitting, expiredTitle, expiredSubtitle, requestAgain, errors.*}, signIn.{forgotPasswordLink, banners.passwordReset.*}}` namespaces.

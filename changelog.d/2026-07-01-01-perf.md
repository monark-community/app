- 2026-07-01: Perf — trimmed redundant per-navigation server work. Two behaviour-preserving wins on the request hot path. (1) The bootstrap-status read was fetched twice on every render — once in the root [layout.tsx](monark/app/services/web/src/app/layout.tsx) (org brand color) and again in the gate layouts via `isSystemBootstrapped()` ; wrapped it in a React `cache()` reader (`getBootstrapStatus` in [bootstrap-gate.ts](monark/app/services/web/src/lib/bootstrap-gate.ts)) so both call sites share one api round trip per request. (2) The client [TrpcProvider](monark/app/services/web/src/lib/trpc-provider.tsx) QueryClient had no default `staleTime`, so every mounted query refetched the instant it remounted during a soft navigation (the App Router keeps the QueryClient alive across routes) ; set a 30s default `staleTime` — mutations still `invalidateQueries` so data stays correct, this only drops the redundant refetches when bouncing between screens. (3) The [authed layout](<monark/app/services/web/src/app/(authed)/layout.tsx>) ran its post-auth reads serially — `isCurrentDeviceTrusted` (itself two serial api calls) then `users.me` ; now the device gate and the deletion-grace `users.me` read fire together via `Promise.all` (the device check still redirects before `me` is used, so `me` is only wasted in the rare revoked-device case), and inside [trusted-device-cookie.ts](monark/app/services/web/src/lib/trusted-device-cookie.ts) the feature-flag check and device lookup are dispatched in the same tick on one client so `httpBatchLink` folds them into a single round trip. Net: the authed layout's post-auth work drops from ~4 serial round trips to ~2 parallel ones, with identical redirect behaviour. The duplicate `getUser` (middleware + layout) was left as-is on purpose — Supabase's SSR guidance requires the layout to re-validate via `getUser` rather than trust the cookie-read session for authorisation.

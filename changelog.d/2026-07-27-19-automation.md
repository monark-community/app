- 2026-07-27: Automation — per-node **error output** (a catch branch), opt-in under a node's Advanced settings. A node with its error output enabled ([contracts/graph.ts](monark/app/packages/automation/src/contracts/graph.ts) new optional `errorOutput` on the node instance ; no migration, it's the JSON graph) grows a second, red **"On error"** output ([automation-editor.tsx](<monark/app/services/web/src/app/(authed)/automation/[id]/automation-editor.tsx>) `FlowNode` + `PortRow` error variant). When such a node throws, the engine ([engine.ts](monark/app/packages/automation/src/server/engine.ts)) now **catches** it: the step is still recorded FAILED (visible in history), but instead of aborting the run it exposes `{ error }` as the node's output, activates the `error` handle, and continues down the error branch — so you can wire failure handling (notify, fallback, etc.). A node without the error output aborts the run as before. Resume-after-delay was updated to treat a caught failure like a success (its error output re-activates on resume). The toggle lives in a new **Advanced** collapsible in the config panel (hidden by default ; triggers don't get one). New `automation.editor` i18n (en + fr: `advanced`, `errorOutputLabel`, `errorPort`, …). New integration test proves a denied node's failure routes to a downstream node and the run SUCCEEDS (16/16 integration + 9 validator unit) ; `typecheck` (web + automation) + `lint` + `check:i18n` (1617 keys × 2) green.

- 2026-09-08: Events: **an event with no org no longer silently fails to route**, and the Data Models events stop claiming an org id that the schema forbids from being null. Both the webhook and the automation subscribers resolved an event's org as "the payload's `organizationId`, else the `userId`'s member orgs, else give up" — so the three events carrying neither (`data-models.schema-changed`, `feature-flag.flipped`, `files.bucket-created`) reached platform-tier webhook endpoints and nothing else, and fired no automations at all. An operator could scope an endpoint to their org, subscribe it to `feature-flag.flipped`, and receive nothing : no error, no delivery row, nothing to explain it. Automation had already paid for this — `feature-flag.flipped` was struck from the trigger picker as "a dead option", while `files.bucket-created` stayed in the picker and could never fire. Both subscribers now fall back to the singleton org, which is what an instance-level fact means in a one-org deployment ; with several orgs live the event stays genuinely ambiguous and is still skipped rather than fanned out to everyone. Separately, `DataModel.organizationId` is a required column ("platform-wide models are disallowed"), yet six record/form events typed their org id `string | null` and `data-models.schema-changed` omitted it — every emit site already passed a non-null value, so the nullability was pure noise that each consumer had to defend against, and the webhook picker documented a null that cannot occur. Those events now carry `organizationId: string`, [data-model-subscriber.ts](packages/calendar/src/server/data-model-subscriber.ts) drops the branch that guarded the impossible state, and [subscribers.ts](packages/webhooks/src/server/subscribers.ts) plus [subscriber.ts](packages/automation/src/server/subscriber.ts) document what the remaining org-less events are and why they legitimately have no org.

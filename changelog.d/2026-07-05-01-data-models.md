- 2026-07-05: Data Models — module integration registry + Calendar materialization. Third slice of [`@monark/data-models`](monark/app/packages/data-models) : `registerModelIntegration(module, { slots, description })` in `contracts/integrations.ts`, mirroring the `registerPermissions`/`registerFlags` idiom — a module declares named "slots" (a type constraint, required-ness, and for `RELATION` a `relationTarget`) and an admin maps a Data Model's own fields onto them per-model via new `trpc.dataModels.integrations.{listAvailable,get,save}` procedures. `upsertModelIntegration` validates the mapping (unknown module, wrong field type, mismatched `relationTarget`, or a required slot unmapped while `enabled: true` all reject) before persisting to the existing `DataModelIntegration` table ; `DataModelSchemaChangedEvent.kind` gained an `"integration"` variant. This is the "mapping, not reserved field keys" mechanism the whole engine is designed around ([polymorphic-db.md](monark/app/docs/features-planning/phase-2/polymorphic-db.md)) — nothing in the generic engine hardcodes any consuming module's name or field-key vocabulary.

  First real consumer : [`@monark/calendar`](monark/app/packages/calendar) now declares two slots (`time`: DATE/DATETIME ; `calendarRef`: RELATION targeting `Calendar`) via `registerCalendarModelIntegration()`, and `registerCalendarDataModelSubscriber()` listens for `data-models.record-{created,updated,deleted}` to upsert / soft- or hard-delete a real `CalendarEvent`, keyed on two new additive columns — `CalendarEvent.sourceModule` / `sourceRecordId` (migration `20260706010000_add_calendar_event_source`, `@@unique` on the pair ; Postgres treats NULL as distinct so ordinary hand-created events, both columns null, are never constrained). Materialized events are `eventType: "PUNCTUAL"` with `startAt === endAt` (the integration maps one "time" slot, not a start/end pair) ; a record that stops satisfying an enabled mapping gets its event soft-deleted, not orphaned. Calendar's own read paths (day view, reminder sweep) need zero changes. `@monark/calendar` gained `@monark/data-models` and (a pre-existing, previously-accidental) `@monark/notifications` as declared dependencies — the latter was imported by `notification-kinds.ts` without ever being listed in `package.json`, working only by hoisting-order luck until this phase's first real vitest module-graph resolution caught it.

  Also fixed along the way : `valueSchemaFor`'s `DATE`/`DATETIME` branch only accepted real `Date` instances, but `DataRecord.data` is JSON — a `Date` written on create survives only as an ISO string on the next read, so `updateDataRecord`'s re-validation of the merged (DB-read) object failed on every date field. Now preprocesses either a `Date` or a valid date string into a `Date` before validating, so both the client (real `Date`s from a picker) and the server (strings from storage) validate correctly. New integration suites : `packages/data-models/tests/integration/integrations.test.ts` (7 tests, slot-mapping validation) and `packages/calendar/tests/integration/data-model-subscriber.test.ts` (5 tests, first integration suite for `@monark/calendar` — it previously had none), plus new `vitest.config.ts`/`vitest.integration.config.ts` for both packages (data-models was missing its unit/integration split entirely until this phase, which briefly caused the integration suite to run — and collide — inside the plain unit `test` script). Full pre-PR gate green across all 18 workspace packages.

- 2026-05-02: LAN-from-phone : avatar + banner img URLs auto-rewrite, api binds explicitly to `0.0.0.0`, CORS rejections log clearly, and the scaffolding doc documents the Supabase-binds-to-loopback caveat. Symptom this fixes : after sign-in on phone the user lands on `/account` but every field is empty / spinner-locked because (1) the stored avatar URL is `http://127.0.0.1:54321/storage/...` which the phone can't reach, (2) the api server _might_ not have been bound to all interfaces, (3) every browser-side Supabase / api call falls into a hung connection because the Supabase Docker containers bind to `127.0.0.1` only. Three things landed:

  **Image src rewrite.** [profile-section.tsx](<monark/app/services/web/src/app/(authed)/account/profile-section.tsx>) + [user-menu.tsx](monark/app/services/web/src/components/user-menu.tsx) now run `me.data.avatarUrl` / `bannerUrl` through `rewriteForCurrentHost` before passing to `<img>` / `<AvatarImage>`. Same loopback-swap helper the tRPC + Supabase clients use ; no-op in production where stored URLs already point at the public Supabase host.

  **Explicit `0.0.0.0` bind for the api.** [services/api/src/server.ts](monark/app/services/api/src/server.ts) `app.listen(env.PORT, "0.0.0.0", ...)` — no longer relies on Node's IPv4/IPv6 dual-stack defaulting to "all interfaces", which depending on platform / Node version can silently bind loopback-only.

  **Dev CORS rejection log.** When `NODE_ENV=development`, an origin that isn't in `WEB_ORIGIN` _and_ isn't a private RFC 1918 IP gets a `logger.warn` line on the api side ("CORS rejected non-private origin in dev — add it to WEB_ORIGIN if intentional") so a developer hitting the api from an unexpected origin sees why instantly instead of debugging a generic 500.

  **Supabase containers bind to `127.0.0.1` — manual workaround documented.** This is a Supabase CLI v1 limitation, not something we can fix in app code. [phase-0/project-scaffolding.md](monark/app/docs/features-planning/phase-0/project-scaffolding.md) gains a "Re-binding Supabase to the LAN" subsection with three options : `socat` reverse proxy (simplest), Windows `netsh portproxy`, Docker `-p 0.0.0.0:54321:8000` re-tag, or upgrade Supabase CLI to a version that supports `host = "0.0.0.0"` in `[api]`. Until one of these is applied, browser-side Supabase calls from a LAN device hang regardless of how clean our URL rewrites are.

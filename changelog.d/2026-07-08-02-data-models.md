- 2026-07-08: Data models — row-level (per-record) authorization. A new `DataRecordRoleAccess` join table ([schema.prisma](monark/app/packages/db/prisma/schema.prisma), migration [20260708000000](monark/app/packages/db/prisma/migrations/20260708000000_add_data_record_role_access/migration.sql)) mirrors `CalendarRoleAccess`: a `DataRecord` with no rows is visible to everyone who can access its model (the default — fully backward-compatible), with rows only the listed roles. Enforcement layers on top of the existing model-level permission check — `listDataRecords` filters by the caller's role ids (`recordRoleAccessWhere`), and `records.getById` / `update` / `delete` / `restore` 404 a restricted record for callers whose roles aren't listed (so existence doesn't leak) ([data.ts](monark/app/packages/data-models/src/server/data.ts), [router.ts](monark/app/packages/data-models/src/server/router.ts)). Data admins (`data-models.manage-schema`, which ADMIN/SYSADMIN short-circuit) bypass the row filter; a blanket `data-models.record-read` does not — row-level is real privacy. `requireModelAccess` now returns the resolved org id so the record procedures build the caller's role-access context (`getUserRoles` + the manage-schema bypass, mirroring calendar). New `records.getAccess` / `records.setAccess` procedures (gated on `manage-schema`) read/replace a record's role list. The authorization integration suite gained 6 row-level specs (restricted-record hidden/404'd for a non-gating role, visible to a gating role, generic-read does NOT bypass, admin bypass, setAccess/getAccess round-trip). No admin UI yet to pick per-record roles (tracked in the README's Deferred). Full gate green (gen, tsc 17/17, eslint 17/17, unit + rbac(40)/webhooks(38)/data-models(43) integration, tiers/modules/i18n).

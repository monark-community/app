- 2026-05-08: Webhooks subscribers integration suite. Closes the second-largest 0 % file in the webhooks package — `subscribers.ts` (the wildcard handler that fans every domain event into the outbox table) was uncovered before this. Floor bumped from 50 → 55 lines, 55 → 60 functions in [tools/merge-coverage.ts](monark/app/tools/merge-coverage.ts) ; webhooks merged coverage moved 55 % → 59 % overall, with `subscribers.ts` itself at 93.5 %.
  - **`@monark/webhooks` subscribers** ([packages/webhooks/tests/integration/subscribers.test.ts](monark/app/packages/webhooks/tests/integration/subscribers.test.ts)). 11 cases against the testcontainer covering every routing rule the wildcard handler enforces. Each spec emits a synthetic event through the real `@monark/common` event bus (`emit(...)`) and counts the resulting `WebhookDelivery` rows ; no mocks — the `findMatchingEndpoints` / `findUserMemberOrgIds` / `findOnlySingletonOrgId` calls all resolve against Postgres so the routing answer reflects what production would compute. Buckets : (1) Registration idempotency — calling `registerWebhookSubscribers()` twice doesn't double-bind the wildcard handler (otherwise every event would fan out 2× and double-deliver). (2) Recursion guard — `webhook.*` events are skipped so a `webhook.delivery-failed` alert doesn't loop back into more deliveries. (3) No-match short-circuit — events with no subscribed endpoints don't enqueue. (4) Rule 1 (platform-tier firehose) — endpoint with `organizationId === null` receives every matching event regardless of payload shape ; covered for both no-payload-id events (e.g. `system.heartbeat`) and org-scoped events. (5) Rule 2 (direct org match) — endpoint at ORG_A receives an event with `organizationId: ORG_A`, does NOT receive one with `organizationId: ORG_B` (the privacy guarantee — over-fan-out across orgs would leak operator-confidential payloads). (6) Rule 3 (user-tied membership match) — user-tied events with no `organizationId` route to org-scoped endpoints whose org the user belongs to (active membership only — ex-members with `leftAt` set are excluded). (7) Singleton-org fallback — when the user has no membership rows but exactly one org exists in the deploy, the singleton's org-scoped endpoint receives the event. The singleton block soft-deletes every other org for its scope and restores them in `afterEach` because the shared testcontainer hosts orgs from sibling test files (data + worker) that would otherwise break the "exactly one" precondition.
  - **Net effect.** `subscribers.ts` lifts from 0 % → 93.5 % covered. Combined with the worker batch earlier today, the webhook delivery seam (subscriber → outbox → worker → receiver) now has end-to-end CI gates from event emission through HTTP attempt + state machine. `router.ts` is the last sizable 0 % file in the webhooks package ; it's tRPC-procedure plumbing that's harder to integration-test without booting a full server, so it'll likely stay covered indirectly via the e2e admin flows rather than via this package's integration suite.

- 2026-05-08: Webhooks worker integration suite. Picks up the load-bearing delivery state machine (`worker.ts` was 0 % covered before this) and locks in every branch the production loop relies on. Floor bumped from 40 → 50 lines in [tools/merge-coverage.ts](monark/app/tools/merge-coverage.ts) ; webhooks merged coverage moved 49 % → 55 % overall, with `worker.ts` itself at 91 %.
  - **`@monark/webhooks` worker** ([packages/webhooks/tests/integration/worker.test.ts](monark/app/packages/webhooks/tests/integration/worker.test.ts)). 10 cases against the testcontainer covering the full delivery state machine. `deliverOne` accepts an injectable `fetchImpl` so we drive every HTTP outcome (2xx success, 4xx retry, 5xx retry, network throw, secret-not-resolved) without standing up a fake receiver. `tickOnce` doesn't accept a fetch override (worker-loop callers don't have one to pass) so the one `tickOnce` case stubs `globalThis.fetch` directly + restores it in a `finally`. Buckets : (1) `tickOnce` returns processed=0 on empty queue, processes a real pending delivery against a 200 receiver. (2) `deliverOne` success path — records attempt + marks delivered + emits `webhook.delivery-succeeded`, resets `consecutiveFailures` to 0. (3) `deliverOne` retry path — records attempt with statusCode + marks pending with `nextAttemptAt` in the future + emits `webhook.delivery-failed{permanent:false}` for 4xx, 5xx, network-throw, and "no plaintext secret available" cases (the secret-store-empty branch records a meaningful error message instead of crashing). (4) Exponential backoff curve — `nextAttemptAt` ≈ `BASE_MS × 2^(attempt-1)` for the first two attempts, never exceeds `WEBHOOK_DELIVERY_BACKOFF_MAX_MS`. (5) Exhausted retries — once `attemptNumber >= WEBHOOK_DELIVERY_FAILURE_LIMIT`, delivery moves to `failed`, emits `webhook.delivery-failed{permanent:true}`, auto-disables the endpoint with reason `"auto-disabled after N consecutive failures"`, and emits `webhook.endpoint-disabled-after-failures`. (6) Already-disabled endpoints don't get re-disabled — the `status !== "active"` guard in `maybeAutoDisable` ensures a manually-disabled endpoint's `disabledReason` doesn't get overwritten.
  - **Net effect.** `src/server/worker.ts` lifts from 0 % → 91 % covered ; `src/server/secret-store.ts` lifts to 51 % (the `rememberSecret`/`resolveSecret` paths get exercised through the worker fixture) ; `src/server/secrets.ts` lifts to 66 % (signing-header generation runs on every successful test). The `subscribers.ts` (event-bus wiring) and `router.ts` (tRPC router) are still at 0 % ; subscribers is the most reachable next target — the rbac / notifications / feature-flags integration suites already established the `_resetSubscribersForTesting` + module-mock pattern that fits.
